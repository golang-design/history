Design. The collector began as gc #0 (1ce17918e3, 2009-01): a single-threaded, stop-the-world mark-and-sweep in mgc0.c over the tcmalloc-derived allocator that had landed a month earlier (e29ce175ed, “malloc in runtime, not used by default”). Marking found block starts through the heap map and a per-block bitmap; sweep walked an explicit allspan list (9f726c2c8b) and returned dead objects to size-class free lists. Early tuning is about making the collector cheaper per object: sweepspan0/sweepspan1 specialisation and inlined free (fb94be55dc), no zeroing of blocks on free (991a968f44), GC clocked on bytes allocated instead of pages in use so fragmentation cannot delay a collection (8ddd6c4181).

The 2011 rewrite 1e063b32cd (“faster allocator, garbage collector”, pauses about half as long, still single-threaded) preceded the first parallel collector: helper threads limited by ncpu (a5f064a3e1), a leak fix in the parallel collector (8219cc9af8), and then in 1.1 the real parallelisation by Dmitry Vyukov: per-M GC stats (d839a809b2), MHeap.allspans as an array so a “parallel for” can partition it (342658bbb6), the parfor algorithm (95643647ae), batch free in sweep (4945fc8e40, 845aa1fc2c), faster mark (b0702bd0db, MaxGcproc 4 to 8; an accidental 16 had been reverted by eb0bc8164a), prefetching in mark (f09e63a2a0), and per-thread work buffers instead of one mutex-protected pool (d4c80d19a8). In 1.4 the same machinery got more threads (MaxGcprocs to 32, 44106a0880, citing parallel roots/stacks, parallel stack shrinking 192bccbf33, per-thread workbuf caches f6f2f77142), non-atomic mark bit updates (0c32bd6262; also when GOMAXPROCS=1, c6fe53a230), and cheaper scan loops (b8fdaaf028, 9dc6764d3c). Deleting code was repeatedly the optimisation: a6d8b483b6 (5-20% faster, suggested by Sanjay Ghemawat) and 03f2189a1b (remove backward bitmap scanning).

Concurrent sweep and proportional sweep

Span: Go 1.3 → Go 1.17 · Status at go1.17: still the design at go1.17 (background bgsweep plus proportional on-demand sweeping and the page reclaimer; sweepone driven by heap_live) → continues as Sweeper termination and pacing (1.18+)

Paths not taken: Asynchronous sweeping for small allocations (never landed)

Design docs & discussion
  • motivating issue #18155 runtime: latency in sweep assists when there's no garbage referenced by 5 of this thread's commits
  • motivating issue #11911 runtime: unbounded heap growth with concurrent GC referenced by 2 of this thread's commits

Design. 3c3be62201 (Go 1.3, Dmitry Vyukov) moved sweep out of the stop-the-world pause: a background bgsweep goroutine plus lazy on-demand sweeping. The commit explains why this was hard: there is no point in time at which the live heap size or consistent malloc/free counts are known, so next_gc, mprof and memstats all become approximate. At the end of GC next_gc is set conservatively to heap_alloc*GOGC, and after each sweep it is decremented by freed*GOGC; the heap must not grow beyond the true value, enforced by two rules: sweeping a span whenever a span is allocated from an MCentral, and sweeping until N pages are freed whenever N pages are requested from MHeap. mprof needed a 3-generation scheme because frees for the previous GC are only known at the end of the next. Each span carries a sweepgen (set atomically before updating span state, 3590d9ce69), and MSpan_EnsureSwept guarantees a span is swept before use (6e612ae0f5). It was disabled the next day (3cac829ff4) and re-enabled after a fix for sweep with preemption on (f8e4a2ef94), followed by a string of race fixes in bgsweep (fed5428c4a, f8c350873c, ea87501750, 6e612ae0f5).

Concurrent mark in 1.5 broke the 1:1 rule (sweep one span per allocated span) because GC now starts earlier: 24a7252e25 finishes sweeping before a cycle starts, fc9ca85f4c makes sweep proportional to span bytes allocated (with a sweep distance, e30c6d64ba), later 7407d8e582, 6383fb6152 and 87d939dee8 fix over-aggressive credit and heap_live underestimates. In 1.8 sweep and root marking of spans became proportional to in-use spans rather than all spans ever allocated (f9497a6747, c95a8e458f, 575b1dda4e), fixing #9265 (a heap blown up to 8 GB then shrunk ran 60x slower). In 1.9 proportional sweep was driven directly by heap_live (a5eb3dceaf) instead of its own byte count and reimbursement. In 1.12 the sweeper gained a span mark bit (ba1698e963) and an efficient page reclaimer (5333550bdc) that uses a per-page in-use bitmap (69e666e4f7) and the arena list (e500ffd88c) to find fully-free spans without sweeping arbitrary spans.

Design. Go 1.4 shipped write-barrier call sites (compiler-inserted, no-ops) while the collector was still stop-the-world. The [dev.garbage] branch (merged for 1.5) added the machinery in steps: concurrent stack scan of goroutines (6184f46ea3, “does not scan running goroutines yet”, finished by a STW with stack rescan), all multi-word barriers expressed via writebarrierptr (b035e97315, which checks the value is not a small non-zero integer to flush out misuse and added the missing barrier for builtin copy), the real barrier and a switch (“if false in func gogc”, d3d60975b4), a coarsened barrier that always greys the destination (28c5385965), checkmark fixes (0584312e7d), and finally concurrent GC on by default with GC-internal structures such as free lists exempt from barriers (8cfb084534). The write barrier was then fixed to a single load-and-compare (32d6fbcb4f, needwb() becomes writeBarrierEnabled) so it can be inlined; barrier code moved to mbarrier.go (4d226dfee9); multi-word barriers use the heap bitmap (4212a3c3d9 typedmemmove, 65c4d7beab heapBitsBulkBarrier).

The phases as they existed in 1.5: sweep termination, concurrent scan (roots), mark 1, mark 2, mark termination. Barriers were enabled by a stop-the-world, replaced by a ragged barrier (bb6320535d) that only requires each P to observe the flag; then moved earlier to the scan phase because stack barriers assumed barriers were on (1303957dbf). Mark 2 (“mark termination preparation”) existed to drain local work caches before STW and was later removed (see 1.12). Mark termination did most of the sweeping setup and finalizer-root and span-root marking; 572f08a064 split span roots into 128 subtasks and 608c1b0d56 moved finalizer-object scanning to concurrent scan, cutting pauses by about 25% vs tip and 50% vs 1.5.1.

Design. Before 1.5 the GC trigger was just next_gc, the heap size at which a STW collection began. Go 1.5’s concurrent GC needed a pacer, and Austin Clements built it in March–August 2015 in mgc.go. Mechanics: the collector tracks heap_live (bytes allocated since the last mark termination plus bytes marked, d7e0ad4b82), marked heap size (50a66562a0), scan work (571ebae6ef, 4e9fc0df48, 8e24283a28), and sets a trigger below a goal (6d12b1780e makes next_gc the heap size at which GC triggers, while the goal is tracked separately). Mutators that allocate during GC must pay in scan work: proportional mutator assist (4b2fde945a) computes scan-work-per-allocated-byte at cycle start from the estimated scan work and the distance to the goal; background workers are scheduled to hit a 25% utilisation target (8d03acce54: dedicated workers plus a fractional worker, idle workers for idle Ps). A proportional-response controller (a0452a6821) replaces the fixed trigger of 7/8*GOGC growth, adjusting the trigger cycle to cycle from the observed heap growth and GC CPU use. Further 1.5 refinements: assist harder when the marked heap exceeds the estimate (170fb10089), reachable heap estimate (4655aadd00, later removed as unstable c8bd293e56), scan work estimated from heap scan size (17db6e0420, with scannable-bytes tracking 3be3cbd548, scalar slots counted 53c53984e7), heap minimum based on GOGC (b6e178ed7e, with a 4 MB floor 813e97b786), assists retried until paid off (8f34b25318), assists allowed during GC start and shutdown (fb5230af8a), revised assist ratio that accounts for heap allocated during the cycle (1fb01a88f9, e3870aa6f3), and GCCPUFraction in MemStats (23e4744c07) user-visible.

1.6 changed assist bookkeeping: per-G assist balance tracked directly (89c341c5e9; the old scheme needed floating point so it could only be checked at span allocation and Gs could run “in the red”), assist before allocating (65aa2da617), preemptible assists (456528304d), park/ready queue (15aa6bbd5a), minimum heap distance via heap goal (9e77c89868). 1.7 allocated black during GC (6002e01e34) and dropped the floating-garbage estimate (c8bd293e56). 1.8 disentangled next_gc from the trigger: MemStats.NextGC is the goal, the trigger is separate (ec9c84c884, 2098e5d39a), and assists can do root jobs (d35dfd405e). 1.9 generalised the trigger (29be3f1999), rationalised triggerRatio (49a412a5b7), consolidated trigger-derived computations (ee175afac2, 1c4f3c5ea0), and stopped adjusting the trigger on forced GC (2919132e1b) or SetGCPercent (227fff2ea4). 1.10 separated soft and hard heap limits (03eb9483e3): until then assists assumed the entire heap was live, so with GOGC=100 the collector worked twice as hard as needed and finished halfway between trigger and goal; the soft goal uses the expected live fraction while the hard goal bounds the worst case. Design. In 1.0 stacks were scanned conservatively word by word. The precision sequence: 1.2 first enabled scanning by frames using stack maps (0e6007e4f9) and in the same release disabled it again because walking frames was about 3x more expensive and the maps were not complete enough to be precise (c3dadca977: “the conservative choice… same as Go 1.1”; benchmarks were added to re-enable it in 1.3); 1.3 moved stack scanning into the parallel mark phase to amortise the cost (0368a7ceb6, noting remaining cost in gentraceback); 1.4 dropped the remaining conservative mode (d208361cde “remove uses of ScanConservatively”) and caches (b91223edd1 cached unrolled GC bitmask). Concurrent stack scan arrived in 1.5 (6184f46ea3, 273507aa8f scan states), with a re-scan in mark termination for stacks mutated after being scanned. To shorten that rescan Go 1.5 added stack barriers (3f6e69aca5 steals stack space for barrier bookkeeping, 306f8f11ad unwinds barriers when writing above the current frame, e9089e4ab6 and 92e68c89f6 document and isolate the code): the runtime hijacks return addresses in frames, so only frames above the lowest barrier hit need rescanning. 1.7 made rescan O(# dirty stacks) rather than O(# stacks) (2a889b9d93: about 34 ns per clean-stack job, exceeding the 10 ms goal near 300k goroutines), stopped rescanning globals (b49b71ae19: up to 500 µs per MB in STW), freed dead G stacks concurrently (e8337491aa), shrunk stacks during concurrent mark instead of mark termination (f11e4eb5cc, 5 ms/MB copied) and removed stack barriers during mark and sweep (269c969c81, 9f263c14ed).

Design. The Yuasa deletion + Dijkstra insertion hybrid barrier (5380b22991) shades both the old value in the slot and (unconditionally for now, because channel ops would need both stacks’ state) the new pointer. Prerequisites landed in 1.7–1.8: barrier before the pointer write (8f81dfe8b4, so the barrier can observe the old slot value), fixalloc zeroing on reuse (ae3bb4a537, to avoid seeing a dead heap pointer), typed memclr operations invoking the barrier, bulkBarrierPreWrite simplification (d8256824ac), and tiny blocks marked at GC start (85c22bc3a5). Effect: worst-case mark termination at GOMAXPROCS=12, excluding stop-the-world time itself, reliably under 100 µs with a 95th percentile around 50 µs (message of bd640c882a). Allocation during GC is black (6002e01e34) which the hybrid barrier requires for stacks.

Go 1.10’s buffered write barrier (e9079a69f3, amd64) replaces the per-write call with a fast path that enqueues the pointers in a per-P buffer without spilling general registers or placing arguments on the stack; only when the buffer fills does the slow path spill all registers and flush (no safepoints or stack splits while the frame is active). Prerequisites: eliminating write barriers from runtime internals that run inside it (d941b07558 persistentalloc, 164e1b8477 recordspan, 3526d8031a gchelper, 070cc8eb02 startpanic_m, 249b5cc945 gcWork methods nowritebarrierrec, 98da2d1f91 wbufptr removal, 42c1214762 alloc/mark bitmaps). bulkBarrierPreWrite (typedmemmove/typedmemclr) then used the buffer (877387e38a: 7.33 → 4.46 ns, buffer of 256), typedslicecopy became one bulk barrier + memmove (6a5f1e58ed), and growslice used the same trick in 1.12 (96dcc4457b, 4363c98f62); in 1.11 all writebarrierptr* calls were eliminated (245310883d). In 1.12 the buffer is poisoned during flushing (fe2feb978e).

Precise heap scanning: type information, the heap bitmap and GC programs

Span: Go 1.1 → Go 1.17 · Status at go1.17: still the design at go1.17 (2-bit/1-bit-per-word sparse per-arena heap bitmap written by heapBitsSetType, GC programs for large types, mark bits in separate per-span bitmaps) → continues as Heap bitmap rewrite and allocation headers (1.18+)

Design. Until 1.1 the collector treated heap blocks conservatively except for flags set at allocation (noscan vs scan). Jan Ziak’s 9204eb4d3c (2013-01, Go 1.1) made the collector interpret type information: when a block’s type is known, the marker walks its pointer layout rather than testing every word; untyped blocks have the collector try to determine the actual type (059fed3dfb); interface values are scanned through their dynamic type (92c153d5f4, 21ea5103a4), channel types are supported by cmd/gc (6e69df6102), and cfe336770b/60682c4f59 replace unions by structs since unions break precise GC. A checker for heap type info (bd1cd1ddea) and a hook to disable precise GC for bisecting problems (709e03f43d) accompanied it; c6293d2106 fixed scanning a slice pointing at an array embedded in a struct, and 54c901cd08 fixed s[len(s):] string pointers that point one past the allocated block. In 1.3 settype writes became lock-free: each MCache owns a span per size class so bitmap updates need no CAS (3b5278fca6).

Go 1.4’s bitmap was a byte array of 4 bits per heap word (ff3fa1b32d, “half the code accesses the bitmap as bytes”), with a cache of unrolled masks for types (b91223edd1, up to 4K cached; perf showed 2% in unrollgcprog). fb44fb6cb7 made type mandatory for scannable allocations. When the allocator and collector moved to Go in 1.5 (1e2d2f0947, automated conversion, followed by 3965d7508e factoring mbitmap.go), 122384e489 removed the boundary bit (finding object boundaries from span element size instead of touching random heap bits; this slowed the garbage benchmark 2%), allowing the bitmap to shrink to 2 bits per word. e375ca2a25 reordered bits as mmmmpppp so 1-bit pointer masks convert directly; feb8a3b616 is the real heapBitsSetType that avoids two atomics per 2-bit field; 4212a3c3d9 makes typedmemmove use the bitmap; ecfe42cab0 keeps pointer bits always set in one-word spans; 9feb24f3ed and 899a4ad47e speed heapBitsForObject (multiply instead of divide; power-of-two masks). 1.5 bitmap bugs: a8ae93fd26 (repeating with large scalar tails), d231cb8249 (slice of GC program repeats n-1 times), 5bfe8adee5 (1.4).

In 1.7 the mark bit left the heap bitmap for separate per-span mark/alloc bit vectors (see allocation thread), freeing the “scan/dead” bit in the first word (a20fd1f6ba reclaims it, simplifying 1/2/3+ word cases) and in 1.9 noscan objects got separate spans, so a noscan test is a span-class test (1a033b1a70, c44d031bf0 removes heapBits.hasPointers, 8e25d4ccef removes heapBitsSetTypeNoScan; 1% gain on go1 and x/benchmarks). 1.11 made the bitmap sparse: one bitmap chunk per 64 MB of heap, indexed through an arena index (c0392d2e7f, 29e9c4d4a4 lays it out forward in memory, f61057c497, b88276da66), splitting object finding from bit lookup (058bb7ea27: heapBitsForObject → findObject + heapBitsForAddr). 1.16 moved checkmarks from the encoded heap-bitmap bits into a separate bitmap (d19fedd180) and added a 24-byte class which required heapBitsSetType to handle objects that are not 16-byte aligned (14c7caae50).

Allocating from mark bits: allocBits, freeindex and ctz

Span: Go 1.7 → Go 1.10 · Status at go1.17: still the design at go1.17 (per-span allocBits/gcmarkBits, freeindex, 64-bit allocCache, nextFreeFast) → continues as Allocation publication, zeroing and preemptibility (1.18+)

Design docs & discussion
  • design doc Proposal: Dense mark bits and sweep-free allocation Austin Clements, 2015-09-30 · listed in Go: A Documentary
  • tracking issue #12800 runtime: replace free list with direct bitmap allocation listed in Go: A Documentary

Design. Through 1.6 sweep built a free list per span by walking the mark bitmap (heapBitsSweepSpan), and malloc popped objects from mcache free lists. The [dev.garbage] work of Rick Hudson in 1.7 removed free lists. Each span has two bit vectors, one bit per object: allocBits and gcmarkBits. GC marks into gcmarkBits; after sweep, the vectors swap roles, so the mark vector becomes the allocation vector (3479b065d4, with helpers dc65a82eff, structs 2ac8bdc52a). freeindex marks the boundary below which all objects are allocated; a 64-bit allocCache holds the inverted allocBits starting at freeindex so that ctz64 finds the next free object (4093481523, 44fe90d0b3), later via the sys.Ctz64 intrinsic (2fb75ea6c6). e4ac2d4acc replaces ref by allocCount; 2063d5d903 restructures alloc and mark bits; 38f674687a reintroduces the no-zeroing optimisation using needzero (previously relying on the sweeper clobbering first two words), 8dda1c4c08 removes heapBitsSweepSpan and moves tracefree/msanfree to the point of reallocation, 6d11490539 restores allocfreetrace via an optional bitmap sweep, b3579c095e revives the sweep fast path, e9eaa181fc makes nextFreeFast inlinable (and 101fbc2c82 again in 1.10). gcBits arenas allocate the vectors (64770f642f); 1.9 made allocation of mark bits lock-free (2ef88f7fcf, 6c4a8d195b) and 1.12 added a span-level mark bit (ba1698e963).

Design. 1.0’s allocator was tcmalloc-like: size classes, MCache per M, MCentral per class, MHeap for pages. 1.1 coalesced zero-size allocations (ec59b840f9) and made mcentral allocation faster by anticipating how many objects are servable (d8626ef128). 1.2: with per-P mcaches, finer-grained transfers were harmful so a whole span moves from MCentral to MCache (23ad563119, noting a 4K span); size-to-class conversion inlined with an int8 table (5a89b35bca); MCache_Alloc inlined into mallocgc (5166013f75); MCache simplified (c4cfef075e, dropping tcmalloc nlistmin thresholds); malloc stats made cheap by counting only frees (5d637b83a9, c075d82cca). 1.3: 8K pages (6d603af6dc, prepared by 327e431057, landed as e48751e217; reduces metadata size and DTLB pressure, ~10% shorter pauses), the tiny allocator combining noscan allocations <16 B into one block (1fa7029425; 10+% fewer allocations on json/garbage; fixes ce884036d2, d18167fefe in 1.6, bf606094ee), slice growth rounded to the allocated block (bace9523ee), prefetch of the next block (d176e3d7c5, 99482f2f9e in 1.5). 1.4: free removed (cecca43804, because it conflicts with bump-the-pointer allocation, “we want to write the runtime in Go”), a transfer cache (e0df11d57e), and heap growth by 64K (0622e13b4d).

Span: Go 1.0 → Go 1.13 · Status at go1.17: replaced by the bitmap page allocator in 1.14 (see “The bitmap page allocator”); the in-use span bookkeeping (spanSet, page reclaimer, in-use bitmap) is still the design at go1.17

Design. 1.0’s MHeap kept free spans in per-page-count lists (free[], up to 128 pages = 1 MB) and one list for larger spans, plus MHeap_LookupMaybe through the heap map, coalescing neighbours on free. Problems: spans larger than 1 MB were on a linked list with O(n) insert/remove (heaps approaching 100 GB), fixed in 1.9 with a treap keyed by size (6e9ec14186, Rick Hudson). 1.12 removed the remaining mSpanList free lists (07e738ec32: now only treaps; “any number of spans totaling the right size” for small allocations, potentially increasing fragmentation), removed busy* lists (b00a6d8bfe), split scavenged from unscavenged spans (b46bf0240c, e508a5f072) and added an iterator (3651476075, 4b3f04c63b, predecessor/successor 5dd4d1f820, 239341f3b6). 1.13 changed the policy to address-ordered first-fit (40036a99a0: the treap becomes address-ordered and also tracks max free pages so find can first-fit; this also makes the scavenger go highest-address-first without extra code; 8c05d67661 fixed find), merged treaps into one (9baa4301cf), made splits in-place on the treap without removal (5c15ed64de), added treapIterFilter so iteration skips irrelevant subtrees (fa8470a8cd: scavenging could be N² otherwise), and provisioned huge-page-aware scavenging (see scavenger).

Design. Michael Knyszek’s #35112 replaced the treap-based allocator (mgclarge.go, mheap.go free structures) by a bitmap allocator in mpagealloc.go. Constants and design comment first (14849f0fa5), then the core (39e8cb0faa, 764 lines in mpagealloc.go plus 32/64-bit variants and tests), still unwired. Packed bitmap summaries (cec01395c5) store three integers in a uint64 per summary: free pages at the start, at the end, and the longest free run, summarised at each level of a radix tree over pallocBits; summarisation of the bit sets later became bit-parallel (4e5ed83e8d, up to 95% faster), as did findBitRange64 (8b8f926fc3, ~2x). allocSpan (a762221bea, which merges allocSpanLocked/allocManual/alloc_m) takes the heap lock only where it must; span initialisation became fully lockless, sweeper metadata atomic (dac936a4ab), and zeroing is decided by per-arena zeroedBase (a120cc8b36, 4208dbef16 lock-free), since a free span no longer carries a “needzero” flag. The scavenger was rewritten alongside (see scavenger). Heap growth was changed to be incremental: f18109d7e3 separates mapping an arena (64 MB) from “growing” the heap, tracking curArena and growing in smaller steps (so heap-growth scavenging, needed for #32828, happens at finer granularity). The switch was a single constant flip, oldPageAllocator (e6135c2768, 2019-10-28), after integration (689f6f77f0); 33dfd3529b removed the old allocator. Follow-ups: sparse chunk index replacing a single giant reservation, which failed on systems with low virtual address limits (acf3ff2e8a), inUse ranges owned by the heap (9d78e75a0a, 1b1fbb3192 maps summary memory only as needed), binary search for findSucc for randomised address spaces such as Fuchsia (76bce1dd52), offset address types so scavenger and allocator see a contiguous space on segmented platforms such as AIX (d69509ff99, ea5f9b666c, 796786cd0c, 55ec5182d7), and sanity fixes (d1798d5aa0).

Design. The first scavenger was periodic (5c598d3c9f, 2012-02): a sysmon-driven pass that released free spans unused for 5 minutes (GC forced if none in 2 minutes) with MADV_DONTNEED on Linux and MADV_FREE on BSD. FreeOSMemory made immediate (e893acf184, 1.3). Scavenged spans needed zeroing (9ad236ab72, 1.1); Windows got SysUnused (4e76abbc60). In 1.5 the scavenger was disabled on 64K-page kernels (f9cc72ccfe) and huge page flags changed only at huge page granularity because MADV_NOHUGEPAGE per released region created too many VMAs and “out of memory” failures (44078a3228). 1.7 aligned scavenging to physical pages (2cdcb6f829, 1151473077) and supported smaller physical pages than the compile-time bound (f407ca9288).

1.12 made it aggressive: scavenged spans separated (b46bf0240c), large spans scavenged before heap growth (c803ffc67d), allocate fairly from free and scavenged (064842450b), then when coalescing merged scavenged with unscavenged spans nearly everything became scavenged, increasing page faults and madvise calls; fixed by not coalescing them (6e9f664b9a), treating allocation from scavenged memory as heap growth that scavenges other memory (8e093e7a1c) and a credit pool for over-scavenging (faf187fb8e). 1.13 introduced the background scavenger (fe67ea32bf, 2018-10 authoring date): a goroutine paced to use 1% of mutator time and paced from the number of scavengable huge pages, aimed at a shrinking heap (the goal falls over time); it removed periodic scavenging (eaa1c87b00) and made the scavenger huge-page aware (a62b5723be large spans first, 31c4e09915 sysHugePage for coalesced free spans, 8c3040d768 call it less often, 1033065ee3/a41ebe6e25 physHugePageSize and shift). In 1.14 with the page allocator: scavenge on growth rather than inline (eb96f8a574), a scavenger that walks the heap backwards once per GC (73317080e1), goal defined by heap_inuse scaled by heap goal ratio rather than next_gc because fragmentation can leave no free unscavenged memory (9b30811280), self-paced (21445b091e: previously externally paced by an assumption about the cost of scavenging a page), no work when <1 physical page (08a72c851c), scavtrace debug flag and scavenge info removed from gctrace (8ac98e7b3f), cost approximation that includes sysUsed (71154e061f), woken on sweep done (2491c5fd24), scavAddr replaced by address ranges (55ec5182d7), and 1.15’s free/scavenged high watermarks so that scavenged and untouched memory is not rescanned every cycle (dba1205b2f, citing heap spikes) and defensive pacing (c7915376ce).

Heap address space: contiguous arena to sparse arenas

Span: Go 1.0 → Go 1.17 · Status at go1.17: still the design at go1.17 (64 MB heapArena units on 64-bit, 4 MB on Windows and iOS, two-level arena map on platforms with large address spaces, arenaBaseOffset, heap-arena hints) → continues as Address-space layout, tagged pointers and the mem.go layer (1.18+)

Design docs & discussion
  • motivating issue #10460 runtime: 512GB memory limitation referenced by 6 of this thread's commits

Design. In Go 1.0 the 64-bit heap was a contiguous reservation with a flat page-to-span map (“heap map in bss”, 4608feb18b; a multi-level table dropped as overkill because there are only 1M entries on 32-bit, 2011) and on 32-bit a fixed arena (70b0de8e98 allows use of more than 512 MB, d37a8b73c5 falls back to a 32-bit allocator if 64-bit mapping fails). 1.1 allocated heap metadata at run time (8a6ff3ab34), limited allocation to 128 GB (9799a5a4fd); 1.2 made the page table lazily allocated, avoiding a 256 MB startup allocation that conflicted with ulimit (671814b904), made mheap static again (8bbb08533d), and made 64-bit heap mapping more flexible (a8ad859c30); 1.3 fixed 32-bit spans array indexing for pointers ≥ 0x80000000 (8da8b37674). 1.5 raised maxmem to 512 GB (43aac4f9e7), added a 128 MB fallback on 32-bit (85d09574fd), tolerated holes (6d1ebeb527) and initial arena reservation failure (324f38a222, 1d5251f707). 1.7 used the entire 4 GB address space on 32-bit (e6ec82067a, same bitmap size). 1.9 untangled _MaxMem vs _MaxArena32 (4af6b81d41, efb5eae3cf) and tolerated non-monotonic arena allocation on 32-bit (13ae3b3a8d), protecting arena bounds from low mmap (e5a5c03f5b), fall back to small mmaps when reservation cannot grow (780249eed4), and map bitmap and spans at initialisation (623e2c4603).

The sparse heap landed in 1.11 as an incremental series by Austin Clements: abstract all mheap.spans access (0de5324d61, a90f9a00ca, 4de468621a), a sparse heap bitmap (c0392d2e7f) and span map (d6e8218581) in 64 MB chunks reached through an arena index, eliminate most arena_* uses (45ffeab549), then 2b415549b8 “use sparse mappings for the heap”: no limit on heap size (previously 512 GB, fixes #10460), no address-space-conflict panics, which could occur for many reasons. ed1959c6e6 offsets the index by 2^47 on amd64 so solaris/amd64’s “negative” user addresses work; ec25210564 adds a two-level arena map for platforms with full 64-bit address spaces (mips64, ppc64, s390x) and to avoid committing large flat maps on Windows; 788464724c reduces arenas to 4 MB on 64-bit Windows where untouched committed memory is charged (a tiny heap committed 64 MB + 32 MB, and 384 MB under race); 51ae88ee2f removes the non-reserved heap logic. 1.12 tracks all arenas in a slice (e500ffd88c). 1.14: darwin/arm64 33 bits (198f0452b0), AIX arenaBaseOffset (5042317d69, a3a630b0d2), Solaris NORESERVE (947f8504d9), and 1.16 more bits on macOS/ARM64 (a739306ca7). 1.17 prepared arenas incrementally (bd6aeca968) and 4 MiB arenas on iOS (e03cca6407).

Mark work distribution: parfor, work buffers, gcWork and root jobs

Span: Go 1.1 → Go 1.17 · Status at go1.17: still the design at go1.17 (per-P gcWork with two cached work buffers, global full/empty lists, markroot jobs for data/BSS/span/stack roots shared by workers and assists) → continues as Mark worker scheduling and GC work queues (1.19+)

GC pacer redesign

Design. The pacer (gcControllerState in mgcpacer.go) predicts when to start a cycle so that marking finishes at the heap goal using only the 25% background workers (gcBackgroundUtilization, and at HEAD gcGoalUtilization equals it). The redesign (proposal #44167) changed two things. First, the heap goal now counts all scan work, not just heap: gcPercentHeapGoal = heapMarked + (heapMarked + lastStackScan + globalsScan) * GOGC/100. Scannable stack is tracked per P and flushed in 8 KiB deltas (9ac1ee2d46), and scannable globals are counted at module load (9da64156a6). Stack and globals scan work also feed the assist credit system. Second, the trigger comes from a single steady-state model: the measured cons/mark ratio, meaning bytes allocated per unit of scan work, normalised by utilization. commit turns it into a runway, consMark * (1-u)/u * (lastHeapScan + lastStackScan + globalsScan), and the trigger is the goal minus that runway, clamped between ~0.7 (minTriggerRatioNum = 45/64) and ~0.95 (maxTriggerRatioNum = 61/64) of the distance from heapMarked to the goal. The minimum bound was raised from the design’s 0.6 to 0.7 because the new pacer “much more consistently hits the goal … leading to slightly less frequent GC cycles, but longer ones”, and tail latency improved by up to 10% (a108b280bc).

Smoothing of cons/mark turned out to be the hard part. The 1.18 pacer ran it through a PI controller. In 1.19, switching to the actual trigger point instead of the precomputed one exploited the controller’s long memory and caused a memory regression (#53738), so the cycle shipped with the precomputed trigger (85a482fc24). In 1.20 the PI controller was replaced by a two-cycle moving average together with the actual trigger (41795528b0). In 1.21 it became a deliberately biased estimator: the maximum cons/mark over the last 5 cycles (lastConsMark [4]float64 plus the current one). This trades slightly earlier, more frequent GCs for fewer assists, and “real production applications showed a reduction in tail latencies of up to 45%” (b513bd808f).

Soft memory limit and GC CPU limiter

Span: Go 1.19 → Go 1.25 · Status at HEAD: GOMEMLIMIT/debug.SetMemoryLimit and the always-on GC CPU limiter shipped in 1.19; the feature flag was removed in 1.21; accounting fixes ran through 1.25

Design. The memory limit is a second heap goal that is compared with the GOGC goal; the lower one wins (heapGoalInternal). memoryLimitHeapGoal starts from the limit and subtracts everything that counts toward it but is not heap objects: nonHeap = mappedReady − heapFree − heapAlloc, plus any current overage. It then keeps a headroom of 3% (memoryLimitHeapGoalHeadroomPercent), with a fixed minimum, and never returns less than heapMarked. The inputs are new, orthogonal accounting: mappedReady, all memory in the Ready state, tracked inside the sysMap/sysUsed/sysFree wrappers in mem.go (4649a43903, f990b0f1e8); heapFree, which replaced the non-orthogonal heap_sys (d36d5bd3c1); and direct totalAlloc/totalFree counters (85d466493d). Because non-heap memory such as goroutine stacks can change between cycles, the goal and trigger are recomputed on each check, and allocManual (stacks, workbufs) can itself trigger a GC (7e4bc74119). The allocator and the scavenger also enforce the limit. The background scavenger keeps a second goal 5% below the limit (reduceExtraPercent), and span allocation runs a synchronous scavenge assist when the next allocation would exceed the limit. That assist time is charged as GC CPU (b4d81147d8).

The GC CPU limiter (mgclimit.go) prevents the death spiral a limit can cause. It is a leaky bucket that fills with GC CPU time (mark- and scavenge-assist time plus the 25% background-worker share while the GC is on) and drains with mutator time, so it caps GC at roughly 50%. Capacity is capacityPerProc = 1e9 ns × GOMAXPROCS, and fill never goes negative, so idle periods earn no credit. While the bucket overflows, assists are disabled and in-flight mark and scavenge assists are cancelled (1f0ef6bec7). The GC may then overshoot the goal. Idle time is subtracted from mutator time, first idle-mark-worker time (08d6c4c2b9) and then all P idle time via pidleget/pidleput (54bd44e573). This lets the limiter engage on over-provisioned machines. In-flight events are read through a per-P packed (3-bit type, 61-bit timestamp) word, so each update only counts CPU time within its own window (d7941030c9).

Green Tea: span-based marking with vector scan kernels

Span: Go 1.25 → Go 1.28 · Status at HEAD: GOEXPERIMENT=greenteagc added off in 1.25, default on in 1.26 (loong64 included later in 1.26); flag and the mgcmark_nogreenteagc.go fallback still present; AVX-512 kernels only on amd64

Design. The classic mark loop greys one object at a time, so access is random and each small object costs at least one cache-line miss plus a separate metadata lookup. Green Tea (1b40dbce1a) delays marking for small-object spans (single 8 KiB page spans whose objects keep heap bits in the span, i.e. objects ≥16 bytes up to 512 bytes; see gcUsesSpanInlineMarkBits) and scans them in batches. Each such span ends in a spanInlineMarkBits block: 63 bytes of marks (“grey”), 63 bytes of scans (“black”), a spanScanOwnership byte and the spanClass. That is enough to scan without touching the mspan. When tryDeferToSpanScan finds a pointer into such a span (checked through a per-arena pageUseSpanInlineMarkBits bitmap), it sets the mark bit atomically. If the object is noscan it is done. Otherwise it tries to take span ownership and enqueues one objptr (span base + object index) for the whole span. scanSpan releases ownership. If only one mark arrived (spanScanOneMark) it scans that single object; otherwise it diffs marks against scans into an ObjMask. With fewer than nelems/8 marked objects it scans sparsely (scanObjectsSmall). With higher density and hardware support it calls scan.ScanSpanPacked, which expands the span’s pointer bitmap by the object mask and writes dereferenced pointers to gcw.ptrBuf in one pass. Before sweeping, inline marks are OR-merged into gcmarkBits (moveInlineMarks).

The kernels live in internal/runtime/gc/scan, imported from Austin Clements’ “gclab” prototype (889ab74169). They need AVX512 VL/BW/DQ/BITALG/VBMI plus GFNI and are generated by mkasm.go. Work distribution changed from the original design: the first version had a fixed-size local span queue spilling half into a locked global span list (1b40dbce1a). In 1.26 this became unbounded per-P spanSPMC rings, which owner and thieves both pop from the tail so objects keep accumulating on queued spans. A work.spanqMask P bitmask is used for stealing and mark-termination checks, and the global queue was removed (d7a38adf4c).

Heap bitmap rewrite and allocation headers

Span: Go 1.20 → Go 1.27 · Status at HEAD: allocation headers are the only heap-metadata scheme (experiment added and defaulted in 1.22, removed in 1.23); GC programs removed in 1.24

Earlier history: Precise heap scanning: type information, the heap bitmap and GC programs (Go 1.1 → Go 1.17)

Design. Up to 1.19 every heap word had 2 bits in an arena-wide bitmap (pointer + “no more pointers”), and type information was unrolled into it at allocation time. Go 1.20 rewrote this to 1 bit per word with word-sized operations and a separate no-more-pointers bitmap (6a9c674a09). Go 1.22 replaced the global bitmap altogether (38ac7c41aa). Objects ≤512 bytes (minSizeForMallocHeader) keep a packed 1-bit-per-word bitmap at the end of their span, written by heapSetTypeNoHeader. Larger small objects carry an 8-byte malloc header holding the *_type. Objects with their own span store the type in mspan.largeType. Pointer/scalar data for header objects is “tiled” from typ.GCData on demand by the typePointers iterator, so nothing is written at allocation and arrays reuse the element mask. The commit cites “a flat 1.5% memory use reduction”. The header sits at the object’s start. Footers (1e250a2199) briefly preserved the implicit 16-byte alignment, but caused an extra cache miss hidden by large L3s in benchmarking, so headers were restored (0ef169abb1). Once types no longer needed unrolling into a heap-wide bitmap, GC programs were removed: the runtime builds large-type bitmaps on demand (45869f5931), and the compiler keeps huge objects out of stack frames (5a0f2a7a7c).

Scavenger redesign

Span: Go 1.18 → Go 1.26 · Status at HEAD: controller-paced background scavenger at 1% of total CPU, chunk-index based search, memory-limit and GOGC goals

Paths not taken: Scavenger and heap-lock experiments before the page allocator rewrite (superseded)

Earlier history: The bitmap page allocator (Go 1.14 → Go 1.17) · Scavenger: returning memory to the OS (Go 1.0 → Go 1.17)

Design docs & discussion
  • proposal #48409 runtime/debug: soft memory limit referenced by 2 of this thread's commits
  • design doc Proposal: Soft memory limit Michael Knyszek · linked from #48409

Design. The background scavenger returns free, unscavenged pages to the OS. It aims for retainExtraPercent = 10 above the GOGC heap goal and, under a memory limit, for 5% below the limit. Since 1.18 its rate is set by a PI controller over measured CPU time, targeting scavengePercent = 1 of total CPU instead of 1% of one CPU (e48e4b4cbb, 6f32d2050d). It works ≥1 ms per batch and does not hold the heap lock while releasing: pages being scavenged are marked allocated and then freed back (4f543b59c5). The 1.19 redesign (91f863013e) replaced the top-down address-space sweep, which “never retreads old ground”, with a lock-free scavengeIndex. The index holds one packed scavChunkData per 4 MiB page chunk (in-use pages, last-cycle in-use, generation, flags), and the page allocator marks chunks as it frees pages, so all scavengers see new work at once. The index costs ~2 MiB per TiB of contiguous heap. Since 1.21, a chunk that reached 96.875% occupancy (scavChunkHiOccFrac) during a GC cycle is hidden from the background scavenger for that cycle and the next. Memory-limit and FreeOSMemory scavenging ignore this.

Design. In 1.21 the runtime took over THP policy on Linux (8fa9e3beee). Finalizers, runtime.AddCleanup and the cleanup queue

Span: Go 1.19 → Go 1.28 · Status at HEAD: AddCleanup shipped in 1.24; cleanups run on up to GOMAXPROCS goroutines since 1.25; GODEBUG=checkfinalizer leak detector since 1.25; misuse panics since 1.26

Design docs & discussion

Design. runtime.AddCleanup(ptr, fn, arg) attaches a specialCleanup to the object’s span, like a finalizer special but without resurrecting the object. Since 1.26 arg is stored in its own allocation; tiny arguments are padded to 16 bytes so they cannot share a tiny block with ptr and keep it alive (1bb1f2bf0c). Cleanup.Stop removes the special (6a2fb15475). In 1.25 cleanups got their own queue (e46c8e0558). Sweepers enqueue into P-local fixed-size off-heap blocks, which are GC roots like finalizer blocks. Full blocks move to a full list, and the last sweeper flushes all local blocks without synchronization. Only whole blocks are dequeued, by a pool of cleanup goroutines. The scheduler wakes them, and when demand exceeds the pool it signals AddCleanup to create another goroutine, up to GOMAXPROCS, because neither the sweeper nor the scheduler can create goroutines. Cleanups may therefore run concurrently (1421b982dc). GODEBUG=checkfinalizer=1 runs a partial checkmark GC from specials only and reports any path from a finalizer/cleanup back to its own object (3df078fc74). Reports are annotated with source and type via a CheckFinalizer special (913c069819), and checkfinalizer>1 adds a scan trace (eec8dd0836).

Design. A weak pointer is a pointer to an 8-byte off-heap handle (atomic.Uintptr), created by getOrAddWeakHandle, which attaches a specialWeakHandle to the object. All weak pointers to one object (at one offset; offsets are uintptr since d87878c62b) share the handle, so weak.Pointer equality is object identity (5ec76ae5aa). Because shading during mark termination would create new non-monotonic GC work, conversions park on work.strongFromWeak.block around the ragged barrier (80d306da50). Linker-allocated and sbrk-mode objects use an “immortal” lock-free handle map instead of specials (6d7cb594b3, 53b9eae387). unique.Make first used a HashTrieMap[T]→weak.Pointer with a background cleanup goroutine (a088e230d4). Object pinning (runtime.Pinner)

Span: Go 1.21 → Go 1.28 · Status at HEAD: runtime.Pinner shipped in 1.21; 1.28 cut pin/unpin costs with batching and per-P caches

Design docs & discussion

Design. Pinner.Pin lets Go memory be referenced from C memory (iovec, io_uring) without copying. The original version (251daf46fb) used a fixed per-span bitmap. In 1.21 pin state moved into GC-bitmap-arena gcBits with two bits per object: pinned, and multi-pinned, meaning a specialPinCounter exists. These bits are copied each GC cycle (697644070c). Cgo pointer checks read the bits without a lock. The *pinner holds a preallocated 5-entry refs array (4bb38fe458) and is cached on the P, which took PinUnpin from 592 ns to 40 ns with zero allocations (0adcc5ace8). A Pinner that becomes unreachable while still holding pins panics. In 1.28 pin-bit updates under the span’s specials lock became plain atomic stores, redundant updates are skipped, unpinning is batched per span (≤64 refs, PinUnpinBatch −38%), and one pin counter is cached per P (91fa326dfe, a69abce146, d6eb7bd6ae, 3544f81e5d).

Sweeper termination and pacing

Earlier history: Concurrent sweep and proportional sweep (Go 1.3 → Go 1.17) · Concurrent mark: write barriers and the dev.garbage collector (Go 1.4 → Go 1.6)

Design docs & discussion
  • motivating issue #45315 runtime: runtime.GC can return without finishing sweep referenced by 1 of this thread's commits

Design. In 1.18 mheap_.sweepers and sweepDrained were merged into one atomic (activeSweep). A sweeper registers only while unswept spans remain, so isSweepDone cannot flap (3aecb3a8f7). bgsweep used to Gosched after every span, emitting trace events every ~30 ns. Stack and register root scanning

Span: Go 1.18 → Go 1.28 · Status at HEAD: allgs snapshot at mark start; async-preemption register state (scalar, vector, LR frame) scanned conservatively

Earlier history: Stack scanning: conservative, precise by frames, stack barriers, hybrid barrier, async safe points (Go 1.1 → Go 1.14) · Hybrid write barrier and buffered write barrier (Go 1.8 → Go 1.12)

Design. Roots are globals (data/bss bitmaps), goroutine stacks (precise via stack maps, conservative for async-preempted frames), finalizer/cleanup blocks and specials. The work here keeps that set complete as the runtime changed: racing allgs growth, new suspendG users (execution tracer, mutex profiling) that can deadlock with STW or race with stack shrinking, and new places where pointers live only in registers at an async preemption point (vector registers used for small moves, the arm64 LR spill frame).

Address-space layout, tagged pointers and the mem.go layer

Span: Go 1.18 → Go 1.28 · Status at HEAD: per-platform heapAddrBits with 9 low tag bits; all OS mapping goes through mem.go state transitions

Earlier history: The bitmap page allocator (Go 1.14 → Go 1.17) · Heap address space: contiguous arena to sparse arenas (Go 1.0 → Go 1.17)

Design. mem.go defines the OS abstraction as state transitions (None→Reserved→Prepared→Ready) with mandatory sysMemStat accounting (f990b0f1e8, 4649a43903). In 1.27 sysUnreserve was added so LSAN root regions are always unregistered, and no sysFreeOS calls remain outside mem.go (40ec033c33). taggedPointer (generalized from lfstack, d959dd97b1) packs a tag into the unused high and low bits. The low bits went from 3 to 9 by requiring 512-byte alignment of taggable objects (9d0320de25).

Linear-memory heaps (Wasm and sbrk platforms)

Span: Go 1.21 → Go 1.27 · Status at HEAD: Wasm and Plan 9 share the sbrk free-block allocator; Wasm uses 512 KiB arenas

Design. On platforms with a single growable linear memory (Wasm, Plan 9) mem_sbrk.go emulates reservations by bumping a break under memlock and keeps a free-block list so sysFreed regions are reused, since memory cannot be returned to the OS. The work reduced waste from aligned reservations and large arenas, which matter for small WASI plugins, and fixed locking.

Heap base address randomization

Span: Go 1.26 → Go 1.28 · Status at HEAD: GOEXPERIMENT=randomizedheapbase64 on by default since 1.26 (off under race/asan/msan)

Design docs & discussion
  • motivating issue #27583 runtime: feature request: Support for ASLR with the heap referenced by 1 of this thread's commits
  • discussion Secure Go binaries golang-nuts · linked from #27583

Design. At init a random heapArenaBytes-aligned address seeds the arena hints. The first mheap.grow picks a random PallocChunkBytes offset, and a random number of pages is marked allocated. The resulting entropy is at least heapAddrBits − PageShift − 1 bits (6669aa3b14).
