Segmented stacks to contiguous (copied) stacks

Span: Go 1.0 → Go 1.4 · Status at go1.17: still the design at go1.17 (stack growth by copying, 2 KB minimum, no segment chain) → continues as Stack growth, stack bounds and the crash stack (1.18+)

Continues in: Goroutine stack growth, shrinking, GC stack barriers and stack objects (Go 1.5 → Go 1.17)

Design docs & discussion
  • design doc Contiguous stacks listed in Go: A Documentary

Design. The first scheme, from 2008, is Ken Thompson’s “segmented stacks AND goroutines” (751ce3a77a): every goroutine starts on a small segment, each function prologue compares SP against a per-G stack guard, and a failing check calls morestack, which allocates a new segment, records the old one in a Stktop header (the “stack top” record: old base, old guard, argument pointer, free flag), copies the incoming arguments over, and runs the function there. On return the function lands in lessstack/oldstack, which pops the segment. The linker (6l pass.c) inserted the check; d3204ef19f and 44f65c8f08 taught the traceback to hop across segments, and later 4b376ef328 made it work through an active lessstack. This is the “hot split” design: a loop that straddles a segment boundary pays an alloc/free per iteration, which is why the segment size became a tuning knob.

During Go 1.2 the default segment size was changed from 4 kB to 8 kB (408238e20b) as an explicit stopgap: the message reports GobEncode -64% and Template -17% on amd64, notes that demand paging means the unused second 4 kB is not resident, and says “khr’s new stacks will avoid needing to make this decision at all”. It was briefly reverted to the old value for the dev cycle and then set back to 8 kB (6aee29648f). Go 1.2 also added a hard limit on stack growth, 1 GB on 64-bit and 250 MB on 32-bit (757e0de89f), so runaway recursion dies with a diagnostic instead of eating the machine.

Contiguous stacks arrive in 1.3. The main commit is 1665b006a5 (“grow stack by copying”, 2014-02-26): GOCOPYSTACK=0 disables shrinking (b8d40172ce); 1a89e6388c consolidates all stack-size and segment-origin bookkeeping in stackalloc/stackfree after finding three bugs (g->stacksize accounting wrong across copystack/shrinkstack, stktop->free not maintained, a FixedStack block that came from the heap being freed into the stack cache); 5daffee17f fixes the size check that looked only at the top segment; 84570aa9a1 rounds stack sizes to powers of two; 1f4d2e79b0 adds efence support. Copying needs exact pointer maps: cfb347fc0a fixes the PC used for liveness lookup (the instruction before the return address, matching what the GC does), 14d2ee1d00 adds a “continuation PC” for frames stopped by a fault (pc after the last deferproc CALL, or 0) because liveness is recorded only at CALLs, and fc6753c7cd/3d1c3e1e26 make defers copyable.

Go 1.4 commits to copying and deletes the old scheme. 15b76ad94b (“assume precisestack, copystack, StackCopyAlways, ScanStackByFrames”) removes the fallbacks (348 insertions, 2893 deletions in 48 files): the Stktop chain, M.moreargp/moreargsize/moreframesize/cret, lessstack, oldstack, many amd64 morestack variants, and replaces stackguard/stackbase/stack0/stacksize/syscallstack/syscallguard/forkstackguard in G by simple bounds (lo, hi). The split prologue shortens because frame/arg sizes are no longer passed. 6c934238c9 lowers the minimum stack to 2 KB (8 KB on Windows, 4 KB on plan9), cutting 100,000 goroutines on linux/amd64 from about 819 MB to 245 MB. The mechanics around it: 92eb1e1600 frees the stacks of Gdead goroutines at GC time, 9198ed4bd6 lets the onM frame be copied (so the goroutine that triggers GC can be shrunk), d6d7170de4 fixes a race between stack shrinking (during mark) and stack-cache flushing, e844f53a01 stops scanning frames/args conservatively (crash instead), and 193daab988 forbids conservative data/bss objects in the linker.

Stack-split prologue, nosplit budget and C-on-Go-stack detection

Span: Go 1.0 → Go 1.4 · Status at go1.17: the prologue check and nosplit budget persist (budget size changed); StackPreempt-style guard poisoning persists → continues as Stack growth, stack bounds and the crash stack (1.18+)

Continues in: Goroutine stack growth, shrinking, GC stack barriers and stack objects (Go 1.5 → Go 1.17)

Design. In Go 1.2 6fa3c89b77 changes the prologue so that after call morestack there is an extra jmp start; the jump is never executed by the CPU. runtime.rewindmorestack decodes it to find the function start, and morestack returns directly to the start label. Effects: newstack can save a coherent goroutine state at function entry, so a traceback at a split overflow works with no special cases; the check is repeated, which doubles as a verification that the new stack is big enough; and rewinding makes preemption possible because the goroutine can resume on its original stack and re-run the check. 031c107cad fixes the linker for large-frame split plus preempt check. Runtime assembly marked NOSPLIT must fit a fixed budget that cmd/ld checks statically (failures such as d83688165a, ddc01d5b06 show the call-chain accounting for notetsleep); the budget grows through Go 1.4: fe91006a02 (+32 bytes), 397bdb216f (to 192), b6951bcc0b (split limit again).

In 1.4 the C-to-Go conversion needs to know that no C code runs on a Go stack. c81a0ed3c5 changes the C prologue (liblink/obj5.c, obj6.c, obj8.c) to compare against a different G word, stackguard1: it holds the normal guard on g0 and gsignal, and ^0 on ordinary goroutine stacks, so the check fails and calls morestackc, which aborts with a message about C code on a Go stack. This is dynamic and covers function pointers; it immediately found sigpanic being pushed onto Go stacks from the signal handlers. 32ecf57d22 rejects onM calls from the gsignal stack (onM assumes it runs on curg or g0, and scalararg/ptrarg are not reentrant); d16a2ad09b makes traceback look past onM and fakes an mstart caller on the rented g0 stack; 1d550b87db allows crashing from the gsignal stack; 12308d5a0b fixes the throwsplit check, which ran on g0 where it was never set. For assembly functions that appear mid-stack, 99f7df0598 makes cmd/gc turn a Go prototype into myfunc.args_stackmap (two bitmaps: inputs live at entry; inputs+outputs after GO_RESULTS_INITIALIZED) and adds GO_ARGS, NO_LOCAL_POINTERS in funcdata.h; 653fb6d872 makes GO_ARGS the default for functions beginning with a middle dot.

Design. Panic, defer, recover and Goexit

Span: Go 1.0 → Go 1.4 · Status at go1.17: replaced by open-coded defers and the new panic loop in later releases (1.14, then 1.22) → continues as Defer, panic and recover re-implementation (1.18+)

Continues in: Defer, panic, recover and Goexit (runtime side) (Go 1.5 → Go 1.17)

Design. In the C runtime, panic.c keeps two stacks per G: g->defer (Defer records, LIFO) and g->panic (Panic records). gopanic runs deferred calls from g->defer; recover is legal only when called directly by the deferred function, and gorecover verifies this through an argp comparison against the Panic. 0de71619ce (Go 1.1) aggregates defer allocations (Defer records allocated in batches and kept on a free list), removing the per-defer allocation and about 30% of the time in BenchmarkDefer (165 to 113 ns, allocs 1 to 0); 72e83483a7 shows cgo calls allocating Defer on the stack.

Two correctness issues dominate the history. First, wrapper methods: for defer iface.M() the compiler-generated wrapper adds a second frame, so recover() returned nil. 7276c02b41 (1.2) adds g->panicwrap, which wrappers bump on entry and decrement on exit, and propagates the Stktop.panic flag forward on stack split. 8473695797 (1.4) throws this out as “fatally flawed” and replaces it with Panic.argp, adjusted on wrapper entry only, so unwinding need not undo anything. Second, copying stacks: f95beae61d makes the GC and copystack both use traceback over the Defer chain, keeps the executing Defer on the list until its arguments are copied (fixing two races and a dangling-pointer bug in copystack), and removes dabort and the untyped allocation; the new tests were TestDeferPtrsPanic, TestDeferPtrsGoexit, TestPanicUseStack.

Go 1.4 converts it all to Go: f44073785a (deferproc/deferreturn), 8217b4a203 (panic and recover, first as panic1.go so the diff was readable, merged in 3a3d47db37), 7006aafdcd preallocates index/slice panic errors, 523aa93288 moves panicindex/panicslice. Semantics fixes: dd740343e0 stack-allocates the Panic struct in 1.3 so panicking does not malloc; f946a7ca09 fixes heap corruption and Defer leaks in recursive panics; 15274e5c9b documents that Goexit cannot be recovered; 0306478fe5 skips already-started defers when Goexit and panic interact; e6708ee9b1/94bdf13497 clear Defer fields before unlinking; 36207a91d3 (with 060a988011 on Windows) makes defer of a nil func panic at the defer statement, and 5032a7dc0c (1.0) gives a distinct message for calling a nil func value.

Design. After the 1.3 contiguous-stack switch, 1.5 added GC stack barriers to avoid re-scanning whole stacks at mark termination: during the first scan, at exponentially spaced points, return PCs are overwritten with a stub (stackBarrier) that records how far the stack has unwound and jumps to the saved PC; the second scan only goes as deep as the lowest barrier that has not been hit (faa7a7e8ae). A 50 MB-heap deep recursion that cost ~150 ms to rescan fell to 10–20 ms mark termination (goscheme from 100–500 ms). The barriers reserved part of every stack (firstStackBarrierOffset), which interacted with shrinking (7387121ddb accounts for the guard when halving) and with cgo (e2bb03f175 forbids a barrier in cgocallback_gofunc’s frame because that slot holds sched.pc). In 1.7, shrinkstack was made safe against concurrent channel operations by locking all channels the G is blocked on and CAS-ing pointers in send/receive slots (276b177771), and shrinking moved from STW mark termination (~5 ms/MB copied + 2 µs/shrink) to the concurrent mark phase (f11e4eb5cc, da153354b2). aed861038f (1.7) adds a stack free list, and 0cbf8d13a7 (1.6) reuses large stack spans (a program that grew to 1 GB stayed at ~30 MB).

Stack barriers became unnecessary once the hybrid write barrier meant stacks are not rescanned, and were removed in 1.9 (d089a6c718, ~1100 lines). Stack-copy cost work: pcvalue cache (see tracebacks), faster readvarint/stackmapdata (aafd96408f), iterating only set bits in adjustpointers (5af0b28a73, 2e7e57770c, 31cfa7f2f2), no write barrier in adjustpointers (a5c3bbe0b4) or in newstack/gogo (shading g.sched.ctxt at scan instead, 3beaf26e4f), and rewindmorestack removed because per-PC SP deltas let the prologue’s re-jump be recorded as frame size 0 (4c9a372946). Go 1.12’s “stack objects” (cbafcc55e8) record every address-taken local in a FUNCDATA and compute liveness at scan time by marking from pointers found in the frame and defer records, replacing “ambiguously live” conservativeness. 1.17 changes growth sizing (b1760f3a27 from 1.15 grows more than 2x when the frame is large; 287c5e8066 fixes the growth loop so copystack is not called redundantly).

Design. Until 1.13 every defer was a heap-chained _defer record with a copied argument frame. 1.8 made the common path cheap: deferproc/deferreturn no longer switch to the system stack on every call (only the slow allocation/free paths do), they are nosplit so preemption and stack growth cannot intervene without acquirem/releasem, and zero-size and pointer-size frames are special-cased (f8b2314c56: runtime defer benchmark -42%, Lock/defer-Unlock overhead 61.4 ns to 27.9 ns; getcallersp as Go helps, d211c2d377). Cgo calls dropped the defer that unwound endcgo, folding it into the callback defer (441502154f). Go 1.14’s open-coded defers (compiler/linker/runtime change that also added funcdata FUNCDATA_OpenCodedDeferInfo, be64a19d99/dad616375f, outside this slice’s list) make the common case inline code; the runtime side is that panic/Goexit must find those frames: gopanic scans the stack for frames with the funcdata, adds a _defer entry on the fly for each (addOneOpenDeferFrame) so open-coded and record defers run in correct order and a “started” state can be stored; on recover the stale entries have to be removed from the chain. Fixes during 1.14/1.15/1.16 show the subtlety: newdefer must not link the record to g0 when called on the system stack (825ae71e56), repeated panic/recover/re-panic left stale entries (fae87a2223), nil deferred function must fault in deferreturn() (22d28a24c8), dumpgoroutine (1f3339f441), and in 1.16 entries must be removed in all cases after recover, aborting the removal loop at any started defer (a5a5e2c968, which explicitly leaves bug 43920 “a more complex fix” open). With GOEXPERIMENT=regabidefer (1.17) deferred functions have the fixed signature func(), so reflectcall of defers becomes a direct closure call (c847932804), frames of defer/go are asserted empty (e0ce0af6ef), and the deferreturn dummy argument is dropped (585b52261c).

Crash handling: startpanic_m never allocates (2edc4d4634), fatalpanic is split into fatalthrow and fatalpanic and the final crash performed outside systemstack so debuggers see a sane stack (b1d1ec9183), and unrecoverable panic handling runs on the system stack (9d59234cbe, 7f1b2738bb, 60a9e5d613). throw on out-of-range index inside runtime (f43aa1df70), and runtime.Goexit uses goexit1 (ad731887a7).

Design. Go 1.14’s non-cooperative preemption splits into (1) delivering a signal to the right thread and (2) injecting a call at the interrupted PC. For (1), suspendG marks the G for preemption and sends its M a “wake up and look around” SIGURG; the handler checks whether the M runs a G with a preemption request at a safe point, counting received preemption signals so suspendG can detect a failed attempt and retry without a back channel (62e53b7922). Targeted M signals were added OS by OS: Linux (334291d1f6, tgkill), BSDs (8714e39497), libc-based OSes (42aab4b0af); Windows uses SuspendThread (b89b4623eb). For (2), sigctxt.pushCall pushes a call to asyncPreempt at the signalled site (2d031dc559, 386/amd64 first), also used to clean up preparePanic; asyncPreempt saves all registers; non-amd64 archs must clobber one register to return from the injected call (REGTMP on arm64/mips/s390x/riscv64, CTR on ppc64) so those sequences are marked non-preemptible (ee330385ca restarts/preempts some instruction sequences; 2ff746d7dc ARM, 1b0b980904 ARM64, a930fede73 MIPS/MIPS64, 374c2847f9 PPC64, 933bf75eda S390X, b89f4c6720 riscv64). MIPS CALL is not atomic: a signal can see updated LR with stale PC, so no preempt there (a930fede73). Debugger call injection reuses the same safe-point machinery (see separate thread).

Defer, panic and recover re-implementation

Span: Go 1.18 → Go 1.28 · Status at HEAD: open-coded + linked defers share one state machine (_panic.nextDefer/nextFrame); recovery transfers to the PC of deferreturn; recover validity is decided by unwinding; still being tuned in 1.28 (linked-defer matching)

Earlier history: Panic, defer, recover and Goexit (Go 1.0 → Go 1.4) · Defer, panic, recover and Goexit (runtime side) (Go 1.5 → Go 1.17)

Design. The 1.18 work made every go/defer target an argument-less func() closure (the compiler wraps calls with arguments). That removed the arg-frame copying machinery: tracebackdefers, the siz argument of newproc/deferproc, variadic defer/go calls, and (after a revert) jmpdefer. deferreturn became a plain loop calling deferred closures, which also deleted per-arch assembly, the PPC64 TOC reload NOP (Ginsnopdefer) and several Wasm special cases. Open-coded defers (frame-local bitmask, funcdata describing slots) stay the fast path; on panic, addOneOpenDeferFrame materialises _defer records for frames that have open-coded defers.

In 1.22 gopanic, Goexit and deferreturn were rebuilt on a shared state machine (_panic.nextDefer, nextFrame, using the unwinder to walk to the next frame with defers), a net −177 lines in panic.go (9eb1d5317b). Follow-ups stopped deferreturn from invoking the unwinder (state for recovered open-coded frames is saved in g.param, 9869699c44), added a linked-defer fast path (51cb12e83b) and restore the caller frame pointer when recovering (b51a4dd6c4, f7a87e3299 for arm64). Range-over-func needed deferrangefunc/deferprocat so a defer in a loop body appends to the parent function’s list (e82cb14255).

In 1.25/1.26 recovery was simplified further: panic recovery now transfers control to the PC of the deferreturn call instead of the old “register-value handshake” in deferproc/deferprocstack (c2ae5c7443, go binary 0.2% smaller), recover() validity is determined by stack unwinding over logical (inlined) frames instead of incrementally tracking argp (7b50024330, 08376e1a9c), and a panic skips ahead to where the previous panic stopped looking for defers (50d988e4e0, which fixes a quadratic-ish repeated-panic walk) with gopanicFP dropped (e93b26688c). Semantics: panic(nil) became *runtime.PanicNilError (aa51c40b1c), whose message later got the runtime error: prefix (16e8e06751).
