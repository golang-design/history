Execution tracer (trace v1): events, per-goroutine sequencing, annotations

Span: Go 1.5 → Go 1.11 · Status at go1.17: still the v1 design at go1.17 (per-P buffers, text of events decoded by internal/trace, go tool trace UI) → continues as The new execution tracer (trace v2): generations, per-M buffers, new parser (1.18+)

Design docs & discussion
  • design doc Go Execution Tracer linked from #16619

Design. The tracer was added in one stack of CLs by Dmitry Vyukov from a design document: a runtime part (traceEvent, per-P traceBuf buffers that are flushed as “batches”, a stack table hashed by PC sequence, a string table), runtime/pprof entry points StartTrace/StopTrace, a trace parser in internal/trace, and the go tool trace command. Events are compact varint-encoded records with delta timestamps; a batch event announces the P and base timestamp, and the parser merges batches and restores a consistent order. Stacks and (later) strings are interned into tables that are written at the end of the trace.

Event ordering was the hard problem. In Go 1.5 the first approach was timestamps (cputicks); because of unsynchronised clocks, VMs, non-x86 timer resolution and identical timestamps this produced flaky tests, so the ordering was made explicit with a global event sequence number (80c98fa901) while timestamps were kept for time display. A global sequencer slowed parallel programs by up to 10x, so in Go 1.7 it was replaced by per-goroutine sequence numbers assigned only to three event types (goroutine start, unblock, syscall exit); the parser rebuilds a partial order (a3703618ea: 5026 ns/op without tracing, 27803 with the global sequencer, 6369 with the new scheme at GOMAXPROCS=48; average event size 4.63 → 3.62 bytes). Go 1.7 also embedded file:line info for stack frames into the trace so it no longer needs the binary (0fb7b4cccd), with a version in the trace header that lets the parser still read 1.5 traces (3fafe2e888).

From Go 1.8 the tracer grew GC visibility (mark worker types, mark assists, STW events, sweep statistics) and in Go 1.11 a user annotation API (Task, Region/Span, Log) that bumped the trace version to 1.11 and required locking the string table.

Race detector integration

Span: Go 1.1 → Go 1.17 · Status at go1.17: still the compiler-instrumentation (racewalk) + TSan-runtime design at go1.17; ports on linux/amd64, darwin, freebsd, windows, netbsd, openbsd/amd64, ppc64le, arm64, darwin/arm64 → continues as Race detector, ASan, MSan and Valgrind integration (1.18+)

Design. The race detector (Dmitriy Vyukov) is the ThreadSanitizer (TSan) runtime linked as .syso files in runtime/race, driven by compiler instrumentation. Under -race cmd/gc/racewalk.c rewrites the AST so that every memory access calls runtime.raceread/racewrite (or the range variants for aggregates), function entry/exit call racefuncenter/racefuncexit, and the runtime calls acquire/release annotations from channels, locks, sync/atomic, goroutine creation and finalizers. Instrumentation is skipped for non-escaping, blank, and zero-sized values and for runtime-internal helpers.

Throughout 1.1 the compiler pass was hardened case by case (nested structs, selectors, arrays, &&/||, for conditions, type switches, append, OKEY, OEFACE), and its cost was reduced: racefuncenter takes its PC directly (ce287933d6, about 46-48% faster on encoding/json), and in 1.3 the cgo-based calls were replaced by custom assembly thunks that extract the caller PC, check that the address is heap or global and switch to the g0 stack (a1695d2ea3: regexp 3.69s → 2.23s, bzip2 9.46s → 4.70s, json 6.38s → 3.63s). In 1.4–1.5 the runtime was converted to Go, so the race detector had to ignore accesses on g0/gsignal stacks (467a6d28be) and race.c became Go (59e3e5354d). In 1.7 the TSan runtime was given per-P contexts, which fixed unbounded growth of sync object descriptors (caa2147532; an alternate procwire scheme was rejected as too messy).

Paths not taken: Background CPU profiling API (never landed)

Design docs & discussion
  • proposal #16093 runtime/pprof: generate profiles in gzipped proto format referenced by 5 of this thread's commits

Design. CPU profiling began (2011) as a hash table in the signal handler (cpuprof) with an eviction log and a legacy binary format read by the pprof tool. Go 1.4 converted cpuprof from C to Go (ac49e6735b) and 1.5 simplified it (3c8a89daf3, 481ce36ec4). The profile format was replaced in Go 1.8: first conversion code from legacy to protobuf (7d14401bcb, f72a629dbd), then CPU (76f12cdaa2), count profiles (ccd69d0582), heap (86ab09eed5) and goroutine locations (c6228ef7e2) were emitted as gzip-compressed pprof protobuf at debug=0. The first implementation buffered the profile three times (in-memory profile, struct representation, marshalled bytes); Go 1.9 added a streaming protobuf encoder so only one copy exists (cbab65fdfa) and switched CPU profiling to a plain sample log (“new profile buffers”, 1a680a902a), with hash-based dedup done in an ordinary goroutine, a more efficient staging hash table (1564817d8c) and symbolization (cbef450df7). Inlining-aware encoding followed (Go 1.9: 9e83c11fca; Go 1.14 corrected inlined functions into one Location with multiple Lines, e038c7e418, e25de44ef2, 71c59ee6fc, and later fadbf7404d expanded the final truncated frame so locations are not split).

The new execution tracer (trace v2): generations, per-M buffers, new parser

Span: Go 1.18 → Go 1.28 · Status at HEAD: default since 1.22 (experiment exectracer2 removed, v1 deleted in 1.23); trace format versions 1.22 → 1.23 → 1.25 → 1.26; flight recorder shipped in 1.25; ongoing hardening and perf work

Design docs & discussion
  • design doc Execution tracer overhaul linked from #60773
  • proposal #60773 runtime/trace: execution tracer overhaul referenced by 10 of this thread's commits
  • tracking issue #66703 runtime/trace: set the v2 tracer as the default tracer referenced by 2 of this thread's commits
  • background Go Execution Tracer linked from #60773

Design. The old tracer (v1) had one global trace buffer list under trace.lock, per-event timestamps from cputicks, and a parser (internal/trace) that had to load the whole trace in memory and order events by timestamps. The redesign (issue #60773, 43ffe2a892) replaces this with generations. Each M owns two buffer slots (previous/current generation); traceAdvance bumps trace.gen, uses a per-M “write flag” (originally a seqlock, d68aec8db1 made it an atomic.Bool store because only the owner thread writes) to prove every M has observed the new generation, then flushes left-over buffers and emits an EndOfGeneration marker. Every generation is self-contained: all live goroutines get a status event (GoStatus, later GoStatusStack), all strings/stacks are in per-generation tables, and CPU samples are routed to per-generation buffers. Events are one byte of type plus LEB128 varints, decoded by a spec table (tracev2.specs). Ordering does not depend on timestamps: each G and P carries a sequence number written into events to encode a partial order (reset every generation); Ms need none because their buffers are already in order. The runtime-side API is traceAcquire/traceRelease + traceEventWriter (traceruntime.go); runtime/trace.go now carries a long invariants list (251814e580).

The parser side (internal/trace, formerly internal/trace/v2) is a streaming Reader that consumes one generation at a time, orders events with the per-G/P/M sequence numbers (order.go), and exposes typed Events with StateTransition info for Go/Proc state changes; stacks are stored as PCs with sharing (d3d390984b, ~400 MiB saved on a busy Staticcheck trace). It also reads the older formats: Go 1.11–1.19 traces are converted on the fly using Gotraceui’s optimized parser (6133c1e4e2).

Supporting data structures: traceMap was rewritten as an append-only concurrent hash-trie (5bba5b256c) because the fixed bucket table “falls over after a few thousand elements”; its traceRegionAlloc got a lock-free fast path. The tracer was made reentrant by making event writing atomic with respect to stack growth, via a small nosplit core (e76353d5a9), which allowed tracing from anywhere in the runtime. Stack capture uses frame-pointer unwinding (separate thread below).

Design. Each sanitizer needs the runtime to tell it about Go memory. The race detector uses prebuilt runtime/race/*.syso TSAN runtimes and ABI-correct racecall trampolines per arch; ASan wrappers asanread/asanwrite (NOSPLIT) are inserted by the compiler, and the runtime poisons/unpoisons allocations; MSan analogously. Valgrind (40b19b56a9) is gated by a build tag and implemented without cgo or Valgrind headers: a tiny assembly function emits the magic client-request instruction sequence. Memory is modeled as a two-level mempool: heap arenas are a pool created with VALGRIND_CREATE_MEMPOOL_EXT (METAPOOL and AUTO_FREE), spans are “superblocks” (MEMPOOL_ALLOC), and objects are MALLOCLIKE_BLOCK; stacks are annotated too.

Design. debug.SetCrashOutput(f, CrashOptions) (1bb947b2eb) makes the runtime write fatal panic output also to a file descriptor (crashFD initialized to -1, guarded against FD changes during panic 638b9023e3), so a watchdog child process can record unhandled panics for telemetry. debuglog (runtime/debuglog.go) is a per-M lock-free ring log; originally the debuglog build tag made the logger type-erased through a const. 548158c4a5 makes the tag select a type alias to dloggerImpl or dloggerFake, so the implementation is always compiled and tested (runtime.a +0.9%, no cmd/go size change).
