Design. The 2008 scheduler (e7d549fbd7, “more fifo scheduling algorithm, newproc will reuse dead procs”) ran all goroutines (G) on a single global run queue protected by one sched lock. Multithreading arrived with d28acc42ec (“first cut at multithreading, works on Linux”): worker threads (M) took Gs from the global queue and an mcpu count limited how many ran Go code at once. $GOMAXPROCS was redefined as “number of CPUs to use, not number of threads” (efc86a74e4) and exposed as runtime.GOMAXPROCS (7955490de2). Every transition (ready, block, syscall) went through the global lock; by 2011 the work was shaving that lock off the syscall path (entersyscall/exitsyscall via atomics, 025abd530e, then xadd instead of cas, ba134539c5).

Go 1.1 replaced this with Dmitry Vyukov’s design: the processor P owns a local run queue, a memory cache and a cache of dead Gs; an M must hold a P to run Go code, and GOMAXPROCS is now the number of Ps. The preparation was done in steps: f20fd87384 introduced park() to atomically unlock a mutex and park a goroutine (removing the racy readyonstop flag that needed the global mutex), e25f19a638 added entersyscallblock, 353ce60f6e local work queues, 6cdfb00f4e per-P dead-G cache and the global runnable queue, and 779c45a507 (“improved scheduler”, a ~1,800 line rewrite of proc.c) made the switch: per-P runnable queues, per-P mcache and G cache, faster non-blocking syscall enter/exit and “more conservative worker thread blocking/unblocking” (idle Ms park, only a bounded number spin looking for work).

From there the work is steady refinement of fairness, wakeup policy and stealing. The invariants that matter: a P with runnable work must have an M looking at it (spinning-M accounting, nmspinning); ready() only wakes another M when no M is already spinning; a P entering syscall is retaken by sysmon after 20us/one sysmon tick and handed off with handoffp; idle Ps live on sched.pidle; runnable Gs overflow from a P’s 256-slot ring to the global queue.

Design. Until 1.2 a goroutine only gave up its M voluntarily (channel, lock, syscall, Gosched) or at GC checks in expensive runtime routines (5328df6534). Go 1.2 added cooperative preemption by reusing the stack-split prologue: setting g->stackguard0 = StackPreempt makes the next function call enter morestack, which turns it into a reschedule. The pieces: a preemptone function (354ec51666), sysmon issuing requests after 10ms of running one G (bc31bcccd3), STW issuing requests every 100us (1e112cd59f), and m->locks reset only after the real unlock so a G holding a runtime lock is never preempted (764bb36ea2). Reliability fixes were needed because the flag could be overwritten by stack growth or lost (5887f142a3, f9066fe1c0). The prologue approach cannot interrupt tight loops without calls, and in Go 1.14 Austin Clements added signal-based preemption: suspendG/resumeG generalized stack-scan suspension (3f834114ab), preemptone sends SIGURG (177a36a5dc), and an asyncPreempt assembly stub spills all user-visible registers (a3ffb0d9eb, generated by mkpreempt.go). A PC is async-safe only if it is not in the runtime, not in an assembly function, and has no “unsafe point” marker; unsafe-point marking was switched from stack map index -2 to the register map so calls can be marked (c3f149250e).

Network poller: from the netFD select loop to the runtime-integrated epoll/kqueue/IOCP poller

Span: Go 1.1 → Go 1.17 · Status at go1.17: still the design at go1.17 → continues as Netpoller (1.18+)

Design. Before 1.1 package net ran its own poller goroutine and Windows used a separate IOCP loop. Dmitry Vyukov moved polling into the scheduler: netpoll(block) returns a list of ready Gs; pollDesc objects (one per fd) hold rg/wg pointers that are either nil, pdReady, pdWait or a G pointer, updated by CAS; deadlines use runtime timers. The scheduler polls non-blockingly in findrunnable, sysmon polls if nobody has for 10ms (6857264457), and an idle M can block in epoll_wait/kevent instead of a futex. The invariant “there must be at least one running P or a thread polling the network” (0b5d55984f) prevents netpoll deadlocks. internal/poll (1.9) then factored the fd lifecycle (fdMutex) out of net and the os package began using the poller for pipes/files (c05b06a12d).

Design. Timers began as a single timerproc goroutine with one global heap (3b860269ee “add timer support, use for package time”; bug fixes dc6726b37f, a899a467f2). Go 1.2 made the heap 4-ary (fcf6a7e5ce), used a monotonic clock for timers on linux (86c976ffd0) and added tsleep overflow handling (3548ab5ebb). In Go 1.10 Aliaksandr Valialkin’s 76f4fd8a52 (“improve timers scalability on multi-CPU systems”) sharded the heap into timersBuckets (one per P, timersLen buckets), each with its own goroutine; goroutines still ran timerproc and had to be woken to run timer functions.

Go 1.14 (Ian Lance Taylor, tracked as #6239 and #27707) rewrote this to put timers on Ps. Each P owns a heap of *timer, a status word timerNoStatus/timerWaiting/timerRunning/timerDeleted/timerRemoving/timerRemoved/timerModifying/timerModifiedEarlier/timerModifiedLater/timerMoving is advanced by CAS and timer.pp points to the owning P. The scheduler calls checkTimers from schedule and findrunnable, which runs expired timers inline on the P (no goroutine), adjusttimers applies modified timers, cleantimers/clearDeletedTimers drops deleted ones lazily, and idle Ps wait in netpoll with a deadline set to the next timer so that time.Sleep and netpoll share one wakeup mechanism. The new code was landed as ~15 bisectable commits that were added but unused until the switch (2e0aa581b4 addtimer, 7416315e33 deltimer, 48eb79ec21 modtimer, eff3c1e426 resettimer, 9093b1def0 dodeltimer, 4665470147 cleantimers, 7d891d5e4d movetimers, 220150ff3c adjusttimers, 432ca0ea83 runtimer), then 6becb03334 switched (“AfterFunc 1.57ms → 0.07ms, After 1.63ms → 0.11ms”) and 580337e268 removed the old code. Later stages were stealing timers from running Ps, avoiding scans and cutting latency.

Design. Channels date from July 2008 (594175d0b5 “chan”, 526200345c synch chan, 2d9ff40774 asynch), select from e963cba8a1, select default from b69e80d8dd, and close in 4523ee9ac8. Semaphores, runtime locks and Notes

Span: Go 1.0 → Go 1.17 · Status at go1.17: still the design at go1.17 (futex/sema lock, note, semaRoot treap) → continues as Runtime mutex: tri-state futex/sema locks → “spinbit” mutex (1.23+)

Design. The runtime had two primitives: Lock (spin then sleep) and Note (one-shot event with notesleep/notewakeup), plus sync semaphores (semacquire/semrelease, published for sync in 5bbd4c2f1b). Early on each OS had its own mutex; ee24bfc058 (Go 1.0) unified them into two generic implementations, futex-based and semaphore-based, each OS supplying a few callbacks (futexsleep/futexwakeup or semasleep). That removed chan finalizers. Notes gained timed sleep (notetsleep, user-goroutine notetsleepg) for preemptive scheduling (Go 1.2: e97d677b4e, e932c2035f) and extra debugging for double wakeups (4380fa6d99, 98d94b589c).

User-level semaphores live in sema.go as a hash table of semaRoots indexed by address. 1.9 fixed scaling for pathological hashing: Russ Cox first made each root a two-level list (O(n²) → O(n) when n goroutines wait on two locks hashing to one root, 45c6f59e1f), then a balanced treap keyed by address (O(n log n) with n/2 colliding locks, 990124da2a), recorded the mutex-event timestamp before readying (b067ad939d) and moved mutexevent profiling out from under the root lock (58d762176a). cansemacquire/semrelease handoff for starving mutexes (1.14) lets Unlock yield to the waiter (a8f57f4ada, relanded 7148478f1b; trace event a4c579e8f7). Go 1.9 also added a runtime rwmutex type (09ebbf4085) working on Ms instead of Gs (80832974ac), used for execLock (9745e88b22) and requiring that Ms holding a read lock not be descheduled (f3b5a2bc19).

Design docs & discussion

Design. Each P owns a timers struct (heap of {timer, when} pairs plus a minWhenHeap/minWhenModified hint used by fast paths) and the scheduler checks it from findRunnable/schedule (runtimer, adjusttimers, cleanHead). Until 1.22 every timer carried a CAS-driven status word with many states (timerNoStatus, timerWaiting, timerRunning, timerDeleted, timerRemoving, timerRemoved, timerModifying, timerModifiedEarlier/Later, timerMoving), so deletion was lazy (“zombies” left in the heap and a deletedTimers count). In Go 1.23 Russ Cox replaced this with a real per-timer mutex plus a few state bits: real deadline always in t.when; timerHeaped if in a heap; timerModified if the heap copy is stale; heap deadline lives in the heap slice itself (bb7a29991c). timers.adjust was rewritten from an O(n) loop plus n O(log n) re-insertions into “mark dirty then re-heapify” in O(n) with no allocation and no multi-timer locking (0728e2b139).

On top of that, the user-visible semantics changed: timers and tickers whose channel is unreferenced become collectable even if still running, because a channel-timer is only in the heap while some goroutine is blocked on its channel (508bb17edd); and Stop/Reset guarantee that no stale value is received afterwards. The implementation models “unbuffered channel fed by a coordinating goroutine”: the real 1-element buffer is hidden (len/cap(t.C) report 0), and Stop/Reset take timer.sendLock, discard a pending buffered send, and report “was active” correctly via an isSending marker (966609ad9e). GODEBUG=asynctimerchan=1 restored the old behaviour until its removal (a5bc606a68). Receives on an idle channel-timer run the timer inline (maybeRunChan) instead of needing a heap entry.

Runtime mutex: tri-state futex/sema locks → “spinbit” mutex

Span: Go 1.23 → Go 1.25 · Status at HEAD: only the spinbit implementation exists (all platforms except wasm); sched.lock is exempt from some behaviours

Earlier history: Semaphores, runtime locks and Notes (Go 1.0 → Go 1.17)

Design docs & discussion
  • design doc Proposal: Improve scalability of runtime.lock2 Rhys Hiltner, 2024-10-16 · golang/proposal
  • tracking issue #68578 runtime: improve scaling of lock2 referenced by 5 of this thread's commits
  • motivating issue #66999 runtime: correct attribution of internal mutex contention referenced by 10 of this thread's commits

Design. The old lock2 was tri-state (unlocked/locked/sleeping) with separate futex and semaphore implementations; with many threads contending for a short critical section every unlock2 saw “sleeping” and woke another thread, which then joined the spin loop on the same cache line (throughput collapse). The final design (fd050b3c6d) unifies futex and sema platforms behind a semaphore abstraction (futexsleep/wakeup implemented as sema ops, 18c2461af3) and adds a “spinning” bit to the mutex word: when a waiter is already awake and spinning, other lockers sleep immediately and unlock2 skips the wakeup syscall. Sleeping Ms form a LIFO stack linked through the word; to bound starvation the bottom of the stack is periodically woken to spin. sched.lock is exempt from most of the new behaviour because Ms use it in sequence for thread-specific work and want low-latency handoff. The most efficient layout needs atomic.Xchg8, so that intrinsic was added for amd64, 386, arm, riscv64, mips64x, mipsx, s390x, wasm (841bb62f19, a8e2ecc8b1, 060bd25310, 58083b57d4, 266b0cff18, e15d14873f, 3c3b8dd4f0). Benchmarks in the commit: geomean 74.3ns→30.3ns (-59%) on one contention microbenchmark and -14.8% on another (13th-gen i7).

testing/synctest bubbles

Span: Go 1.24 → Go 1.28 · Status at HEAD: GOEXPERIMENT removed in 1.26; all bubble violations are fatal; Test-style API

  • proposal #67434 testing/synctest: new package for testing concurrent code referenced by 7 of this thread's commits
  • proposal #69687 testing/synctest: experimental package for testing concurrent code referenced by 2 of this thread's commits

Design. A bubble is a tree of goroutines with a private fake clock. The runtime tracks bubble membership per g, marks goroutines blocked on channels, sync.Cond, sync.WaitGroup, timers, select{} as durably blocked; when every bubbled goroutine is durably blocked, the bubble’s clock jumps to the next timer; if no timer exists a deadlock panic is raised. Channels record the creating bubble (hchan.bubble), so cross-bubble operations are detectable. Timers inside a bubble live in a per-bubble heap and run when the bubble is idle. WaitGroups are associated with a bubble at first Add and only durably block Wait while associated (b170c7e94c), and are disassociated on Wait (9ae38be302).
