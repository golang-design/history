Paths not taken

Part III · 39 efforts that did not land in the form attempted

Parts I and II only cover work that landed. This part covers work that was built or designed and then did not land in the form attempted: the request-oriented collector, lock-free channels, a NUMA-aware scheduler, the generics prototypes that came before the shipped design, and many smaller attempts. Each entry says what was tried, how far it got, and why it stopped, citing the record. Where the record gives no reason, the entry says so.

Outcome labels.

  • never landed The idea is still absent from Go.
  • superseded The problem was later solved by a different design, which is linked.
  • partially landed Some pieces made it in, the core did not.
  • landed later A later version of the same work landed years after the attempts described here stalled.
  • still open The proposal or CL series has had activity in the last year; the entry covers the attempts so far.
  • dormant The work is still open (CLs open, or a proposal on hold) but has had no activity for a year or more.

How the efforts were found.

  1. Gerrit (2015 on). Every never-merged change in the in-scope directories was fetched, including old path names. Changes were dropped when a landed commit carried the same subject or Change-Id, or when they sat on release branches. That left 4,223 CLs: 3,054 abandoned and 1,169 still open. They were grouped mechanically into 781 candidate clusters (1,983 CLs), by shared issue, Gerrit topic, dev branch, or same author and package within 90 days.
  2. Rietveld (2009–2014). The pre-Gerrit code-review site was searched for CLs by the core runtime and compiler authors (18,874 CLs). This gave 427 in-scope CLs that were never submitted, 364 of which have no landed commit with the same subject.
  3. Branches. Every dev branch was compared with master. Three kinds were set aside:
    • the dev.boringcrypto branches, which are out of scope;
    • branches whose content landed as rewritten commits (dev.typealias, dev.gcfe);
    • one- and two-commit leftovers (dev.inline, dev.types, dev.tls, dev.link, dev.simd).
    The unmerged work that remains is on dev.garbage (ROC) and dev.go2go (the generics translator).
  4. Proposals and design docs. The search covered 327 runtime, compiler, linker, sync and reflect proposals that were never accepted (declined, withdrawn, on hold or open), and the design docs in golang/proposal and the curated Google Docs that no landed thread cites.
  5. Reading. Six Claude Sonnet readers went through all of the above and proposed 225 candidate efforts. Candidates were then:
    • merged across sources (for example ROC, which appears on Gerrit, on dev.garbage and in the README);
    • checked against the full landed history with fuzzy subject matching. This dropped 33 that had in fact landed under different wording, such as batched write barriers in Go 1.21, or were duplicates.
    The result is 39 written entries, 101 smaller attempts in per-topic tables, and 25 recent items listed as still open. Claude Sonnet wrote the entries from evidence packs: each pack held the CL messages, the non-bot review messages, the issue and proposal discussions and, where they exist, design docs and talks by the people involved. Unlike Parts I and II, this part draws on review discussion and design documents, not on commits alone.

Gaps.

  • Lost review reasons. Many old CLs were closed in bulk cleanups, for example in 2018, with the bare message “Abandoned”. For those, the reason a CL stopped is not in the record.
  • Rietveld coverage. The Rietveld search could not reach every author. Notably, Rick Hudson’s and Dave Cheney’s pre-2015 Rietveld histories, and that of the author of the 2012 precise-GC patch, are missing.
  • Outside scope.
    • Language proposals with no compiler or runtime prototype, such as check/handle without code. The error-handling entry covers them only because try and ? had prototypes.
    • Work done only on mailing lists or in private branches.
    • Out-of-scope directories such as cmd/go.
  • Unreviewed table summaries. The small-attempt tables come from the first-pass reading and were not reviewed entry by entry.

Memory management

Request-oriented collector (ROC)

never landed 2015-10 → 2017-05 · Rick Hudson, Austin Clements · 16 CLs

Design docs, proposals & discussion
  • design doc Request Oriented Collector (ROC) Algorithm
  • talk Getting to Go: The Journey of Go's Garbage Collector (Rick Hudson, ISMM 2018 keynote)

What was tried. The request oriented collector (ROC) rested on the “request hypothesis”: objects created while serving a request tend to die when the request ends. The design doc “Request Oriented Collector (ROC) Algorithm” (Hudson and Clements, June 2016) tracked each goroutine’s allocations between an initial and a current sweep pointer in the span’s mark bitmap. A write barrier kept the invariant that every “published” object (one reachable from another goroutine or from the shared heap) had its mark bit set, transitively marking the referent before the pointer was installed. When the goroutine exited, resetting the current sweep pointer to the initial one freed all unpublished objects without a GC cycle.

How far it got. Hudson started with “direct bitmap allocation” (CL 15560, October 2015, +2041/-232, lit up with GODEBUG=gctoc=1), which its message called “roughly code complete” but “not debugged so don’t expect to run anything”. From April 2016 the work moved to the dev.garbage branch as a series of small CLs: the publish write barrier (CL 22343), the checkpoint/rollback code (CL 22345), startG/recycleG/publishG (CL 25212, CL 25260, CL 25303), stack-pointer publishing (CL 25304), counters and trace output (CL 33312, CL 33318) and a GODEBUG=gcroc=n switch (CL 33319). The last CL in the record, lazy publish on syscall (CL 37101), dates from February 2017. All were marked “DO NOT REVIEW” or work in progress.

Why it stopped. No CL or review message states a verdict. The reason comes from Hudson’s ISMM 2018 keynote (“Getting to Go”), which he introduced as “our failures”. He said ROC’s write barrier “was always on”, and that publishing a private object meant a transitive walk that “could cause many cache misses”. The RPC benchmark scaled well with ROC enabled, but the compiler benchmarks were “exactly the programs that ROC did not do well at”, with “30, 40, 50% and more slowdowns”, which he called unacceptable because “Go is proud of how fast its compiler is”. On the wider benchmark corpus, “the numbers were uniformly bad and ROC wasn’t going to become a winner.” He added: “It’s true we scaled but we only had 4 to 12 hardware thread system so we couldn’t overcome the write barrier tax.” The CL records show only the later clean-up: Hudson abandoned the accidental master-branch re-uploads on 2017-03-29, and in October 2018 Brad Fitzpatrick closed several of the dev.garbage CLs with the bare message “Abandoned” (others stayed open as work in progress).

Lessons. Hudson’s conclusion was that ROC “was a losing proposition” on 4 to 12 thread machines, because the write barrier tax outweighed the scaling gain. He said that on “128 core systems” the scaling might be a win and “we might come back and revisit this”.

Non-moving generational GC with card marking

never landed 2017-04 → 2019-03 · Rick Hudson, Austin Clements · 15 CLs

Design docs, proposals & discussion
  • talk Getting to Go: The Journey of Go's Garbage Collector (Rick Hudson, ISMM 2018 keynote)

What was tried. After ROC, Hudson tried a non-moving generational collector that kept Go’s latency goals. It used what Hudson called “sticky bits”: an object with its mark/allocation bit set was mature, an unset one was young, and a minor GC promoted a young object by setting its bit when a mature object pointed to it, with a transitive walk. A fast buffered write barrier flushed pointers into a card table when no GC cycle was running. A second variant, from Austin Clements, did card marking without a write barrier: it kept a hash of the mature pointers in each card, so a changed hash marked the card dirty. This exchanged write-barrier cost for hashing cost.

How far it got. The work was Hudson’s scratch CLs, all “DO NOT REVIEW” or “DO NOT SUBMIT” and none merged: heap characterization for a June 2017 design doc (CL 47270, CL 56592), card-marking types (CL 56591), a “generational scratch pad” (CL 65010) and card marking (CL 105357). CL 105367 dropped card marking entirely and scanned the whole mature space. In September 2018 a chain began with CL 137476 and continued with CL 137478, CL 137479 and CL 137482, adding full-versus-generational scheduling and card shards. Clements prototyped card marking in the write barrier (CL 40294) and an inlined version (CL 40295, “This code is awful”). The last CLs only measured young-object mortality (CL 159377) and pointer hashing time (CL 162159).

Why it stopped. In the ISMM 2018 keynote Hudson said that on Go’s own benchmarks “things didn’t go as well”: “The write barrier was fast but it simply wasn’t fast enough,” and it was hard to optimize because with a safepoint at every instruction “there really wasn’t any write barrier that we could elide”. He added that escape analysis keeps young objects on the stack: “It isn’t that the generational hypothesis isn’t true for Go, it’s just that the young objects live and die young on the stack.” He also argued that growing the heap lowers mark cost below a write barrier’s constant cost. For the hash-based card variant he reported “a couple of outliers” on the performance benchmarks. In the review of CL 137482 on 2019-03-15, Hudson wrote that using hashing “to filter out cards that don’t need to scanned is not as effective as we had hoped”. The excerpt does not record a final decision to stop; every CL stayed open.

Lessons. Hudson said generational GC “greatly reduces the long STW times of full GC cycles but it doesn’t necessarily improve throughput”, and Go, having no such stop-the-world problem, had to look at throughput. He also named the write barrier as the obstacle (“Gee wouldn’t this be great if it wasn’t for the write barrier”).

Allocation-site lifetime prediction and goroutine-local heaps

never landed 2015-02 → 2023-06 · Dmitry Vyukov, Michael Knyszek, Austin Clements · 3 CLs

What was tried. Three separate prototypes tried to use object lifetime or ownership information in the allocator. Dmitry Vyukov’s “allocation site learning” (CL 5290, February 2015) referred to a Google Doc design. Michael Knyszek’s prototype (CL 251060, August 2020) predicted which allocation sites produce short-lived objects, defined as objects that “die before the GC can mark it the first time”, so they could be separated from long-lived ones. Austin Clements’s experiment (CL 501315, June 2023) measured “perfect goroutine-local heaps”: each object was owned by its allocating goroutine, and the GOEXPERIMENT=cgocheck2 write barrier detected when allocations leaked between goroutines.

How far it got. All three were small prototypes marked “DO NOT REVIEW”. CL 5290 was +244/-142. CL 251060 was +380/-33 and was kept in the work-in-progress state. Its message listed its own weaknesses: a dynamic allocation-site index about “~4x binary size”, two-level lookup, and incomplete coverage (maps and reflection were not handled). It said a compiler-generated site index would be much smaller and would avoid the lookup. The predictor ran only while the GC was off, to avoid skew from objects allocated black. CL 501315 was +587/-9. No measurement results appear in the CLs.

Why it stopped. No reason is recorded in the CLs. None of the three has a review message giving a verdict. Russ Cox asked in April 2015 that CL 5290 be labelled “DO NOT REVIEW” to keep it off review dashboards. On 2017-02-24 he abandoned it with the message “Two years old, abandoning to avoid appearing in search results on Gerrit”, a housekeeping closure that states nothing about the idea. CL 251060 and CL 501315 remain open. No design doc, issue or talk discusses results from any of them.

Heap limits before GOMEMLIMIT: SetMaxHeap, GC backpressure, a memory target

superseded 2017-06 → 2021-11 · Austin Clements, Michael Knyszek · 2 CLs

Design docs, proposals & discussion
  • design doc User-configurable memory target (Michael Knyszek)
  • proposal #21795 proposal: runtime: memory awareness exposure in runtime like Objective-C `didReceiveMemoryWarning`
  • proposal #23044 proposal: runtime: add a mechanism for specifying a minimum target heap size
  • proposal #29696 proposal: runtime: add way for applications to respond to GC backpressure
  • proposal #37452 proposal: runtime: mechanism for monitoring system memory
  • proposal #44309 proposal: runtime/debug: user-configurable memory target

What was tried. Several designs let programs control heap size before GOMEMLIMIT. SetMaxHeap (CL 46751) set a soft limit that used “the lower of the GOGC-computed GC target and the heap limit”. Because the GC could no longer amortize its cost against heap growth, callers had to register for notifications that the collector was under pressure and “shed load”. #23044 asked for the opposite, a minimum heap target. #29696 (opened by josharian as a discussion) asked for a way to respond to GC backpressure. Knyszek’s design doc “User-configurable memory target” (#44309, February 2021) proposed debug.SetMemoryTarget, a hint of total Go memory use that the pacer would turn into a heap goal.

How far it got. Clements’s SetMaxHeap CL (June 2017, +459/-35) went through about 22 patch sets and was rebased onto Go 1.14 in April 2020, but it kept “DO NOT SUBMIT” and its stated purpose was “to get some experience with the API and figure out if this is even a reasonable primitive”. It absorbed Knyszek’s fixes, including the lock-order deadlock fix CL 156917. The memory-target proposal drew support from one reviewer but was never implemented.

Why it stopped. On #23044, Russ Cox closed the minimum-heap request on 2020-02-26 in favour of #29696. Cox later explained: “if we evaluate every single API in isolation, what you end up with is a LOT of APIs, each of them justifiable on its own but collectively not.” Knyszek wrote that a fixed minimum “unfortunately not as simple” because it causes “significant issues with the GC pacer”. On #29696, Cox wrote in June 2020 that SetMaxHeap was built for backpressure, but “the people who have tried it and used it are all not watching for or responding to backpressure”. That issue is still open and on hold. Knyszek postponed the memory-target doc after the pacer redesign slipped (“I definitely need to push this back”, 2021-04-15), then withdrew it on 2021-11-10: “Given that #48409 has been accepted, and I haven’t received any feedback … that this would better suit some use-case, I’m going to withdraw this proposal.” Clements’s reply on #21795 (2017) noted that Linux has no memory-warning API; that issue was closed by a bot after a timeout.

What landed instead. The soft memory limit (#48409) shipped as GOMEMLIMIT and debug.SetMemoryLimit: see Soft memory limit and GC CPU limiter.

Arena API prototypes, 2017–2022

partially landed 2017-09 → 2022-08 · Austin Clements, Keith Randall, Dan Scales, Michael Knyszek · 7 CLs

What was tried. A series of proof-of-concept arenas gave programs a way to allocate groups of objects with a shared lifetime and free them at once. Austin Clements’s first version (CL 63651, September 2017) was “a simple, type-safe arena allocation API” meant for “deserializers of irregular structures, which often have to construct complex and irregular object graphs, all with very similar lifetimes”. It was built in the runtime and reflect packages. Later versions kept that shape and varied the runtime support.

How far it got. Keith Randall’s version (CL 114002, May 2018, +264) was based on Clements’s. A CL titled “Dan’s arena” (CL 224577, March 2020, +941/-702) followed. Dan Scales’s amd64 prototype (CL 387975, February 2022, +1228/-38) was “a sample implementation of arenas” that “may have various issues and limitations”. Michael Knyszek then wrote CL 390035 (fault, rather than unmap, freed arena address space) and CL 390036 (recycle arena address space once no pointers remain), and CL 423358 (August 2022, +1041/-60), an arena package behind GOEXPERIMENT=arena, “based on one by” Scales. Each earlier CL was labelled “DO NOT REVIEW”; the first two were described as “not documented or fully tested”.

Why it stopped. No reason is recorded in the CLs for the early prototypes; they were left open as experiments. CL 423358 was closed by Knyszek on 2022-08-12 with the bare message “Abandoned”, and the record gives no explanation for it. Open prototypes CL 63651 and CL 114002 show no verdict, only a 2018 review from Patrik Nyblom about getting CL 63651 to run.

What landed instead. An arena package landed as an experiment, not as these CLs: see Memory arenas experiment.

Asynchronous sweeping for small allocations

never landed 2018-10 → 2018-11 · Austin Clements · 1 CLs

What was tried. Clements’s CL 138962 restructured sweeping so object reclaiming left the allocation critical path. Before it, taking a span from an mcentral could sweep “an unbounded number of spans” to find free space, which put sweeping on the allocation path, caused convoys across Ps, contended on mcentral locks and was non-preemptible; the message cited “5+ second effective STWs for dense 100+ GB heaps”. The CL had allocation do only the proportional sweep needed to finish before the next mark, allocate from known-free space, and otherwise grow the heap. It also made span ownership explicit and removed the “backwards ‘empty/nonempty’ terminology” in mcentral.

How far it got. One CL (+176/-156, master branch) was uploaded in October 2018 and revised through at least November; it was the first of a stack of CLs. Reviewers were Dmitry Vyukov and Rick Hudson.

Why it stopped. Vyukov raised a concern on 2018-10-06: if full spans are not swept before allocating, it “can also easily triple or even quadruple heap size with GOGC=100, and this in turn means killed jobs”. Clements replied on 2018-11-09 that the CL still sweeps full spans; “the effect of this CL is just that we’re less willing to spend a really long time sweeping and more willing to grow the heap instead”. Hudson asked for comments on the locking protocols (2018-11-13). The record does not show the concern being resolved. The CL was abandoned on 2023-06-22 by Dmitri Shuralyov in a bulk clean-up of the stack, whose tip CL 148898 had been closed with the rationale “Cleaning out very old changes. If the change is still relevant, please submit a new CL for re-review.” No technical reason is recorded.

Scavenger and heap-lock experiments before the page allocator rewrite

superseded 2018-10 → 2019-12 · Michael Knyszek · 13 CLs

What was tried. Between October 2018 and December 2019 Knyszek tried many ways to make scavenging (returning free memory to the OS) prompt without hurting allocation latency, mostly by shrinking how long the global heap lock was held. Examples: marking freshly mapped memory as scavenged (CL 140197), eagerly scavenging by a global debt budget (CL 141937), dropping the heap lock around scavenging syscalls (CL 142957, CL 172478, CL 185617), scavenging least-recently-used spans (CL 160498), a pairing heap (CL 160497), tracking spans larger than a huge page separately (CL 170859), and unscavenging without the heap lock (CL 184442). It also included reintroducing mSpanLists for small spans (CL 151538, fixing #28479).

How far it got. Thirteen CLs, most of them +10 to +220 lines, were uploaded against #16930, #14045 and #30333. CL 151538 had two Code-Review+2 votes before they were removed on 2019-04-05. None of the series landed in this form.

Why it stopped. The abandon messages give short reasons. CL 140197: “This potentially breaks the property of HeapReleased that it is the lower bound of non-backed pages.” CL 141937: “Not necessary.” CL 142957: “There are better ways to do this.” CL 160498: “No longer necessary.” CL 172478: “Stale and not relevant.” CL 151538: “Should be unnecessary for the most part.” CL 170859: “Superceded by 170860.” CL 176957 (counting the scavenger as idle for deadlock detection) was abandoned as “Superseded by golang.org/cl/177097” after Knyszek wrote on #31966 that Ian Lance Taylor “noted offline that the deadlock detector already doesn’t work for many people in many situations”, so it was better to mark newly mapped memory as scavenged. CL 207999 was abandoned on 2019-11-21 with no message. CL 212639, “disable the scavenger”, was an open “DO NOT SUBMIT” scratch change.

What landed instead. The heap-lock problem was removed by the bitmap page allocator, and the scavenger itself was reworked in Scavenger redesign.

Persistent-memory Go (go-pmem)

never landed 2021-01 → 2021-02 · Jerrin Shaji George, Mohit Verma, Rajesh Venkatasubramanian · design and discussion only

Design docs, proposals & discussion
  • design doc 43810-go-pmem.md (Jerrin Shaji George, Mohit Verma, Rajesh Venkatasubramanian, Pratap Subrahmanyam)
  • proposal #43810 proposal: spec: add native support for programming persistent memory in Go

What was tried. The go-pmem proposal (#43810, design doc “43810-go-pmem”, January 2021) added native support for persistent memory (byte-addressable, durable memory such as Intel Optane) to a fork of Go 1.15. It had a garbage-collected persistent heap, with mspan gaining a memtype field and separate mcache/mcentral/mheap metadata for persistent and volatile spans. Allocation used new keywords pnew and pmake, and a txn block marked crash-consistent updates, which the compiler instrumented through a new SSA pass. Allocator and GC metadata were stored in the persistent arenas so the heap could be recovered after a restart.

How far it got. The authors had a working implementation (jerrinsg/go-pmem, described in a 2020 USENIX ATC paper) and reported that a Redis built with it offered “more than 5x throughput compared to Redis running on NVMe SSD”. Only the proposal was submitted to Go; no CLs against the Go tree are in the record. The design doc itself listed downsides, including the persistent metadata layout being tied to the allocator’s data structures.

Why it stopped. The proposal was declined. Early comments objected to the new keywords. Ian Lance Taylor asked whether a single root was sufficient, what a failing transaction means, and what stops a persistent object from holding a pointer to volatile memory. Other participants argued that a file-like API in a package would do, since on Linux persistent memory is a mapped file. On 2021-02-03 Russ Cox wrote that “we should probably decline this full proposal but could easily add the MAP_SYNC flag and perhaps even the ‘flush memory region’ operation”, and marked it a likely decline. After the authors replied that direct load/store access to a DAX mapping is what gives the performance, Cox closed it on 2021-02-10: “No change in consensus, so declined.” He invited separate proposals for MAP_SYNC and a flush API.

Scheduler and concurrency

Lock-free channels and finer-grained select locking

never landed 2011-08 → 2015-04 · Dmitry Vyukov · 7 CLs (6 on Rietveld)

Design docs, proposals & discussion
  • design doc Go channels on steroids
  • discussion golang-dev: update on "lock-free channels"
  • tracking issue #8899 runtime: lock-free channels

What was tried. Dmitry Vyukov redesigned channels around lock-free fast paths. In his January 2014 design doc “Go channels on steroids”, buffered channels became a ring buffer whose send and receive positions (sendx/recvx) are advanced by CAS, with a per-element “lap” counter telling producers and consumers whether a slot is ready; the mutex remained only for wait queues. NUMA-aware scheduler

never landed 2014-09 → 2015-04 · Dmitry Vyukov · 1 CLs

Design docs, proposals & discussion
  • design doc NUMA-aware scheduler for Go

What was tried. Dmitry Vyukov’s September 2014 design doc “NUMA-aware scheduler for Go” proposed making the runtime topology-aware. The heap, global run queue, stack caches and pool of Ms would be partitioned per NUMA node; Ms would be hard-bound to nodes and Ps strictly partitioned between nodes, with a lastm field to keep P-to-M affinity. Work stealing would prefer the same node (per-node queue, then Ps on the node, then remote nodes), local scheduling would become mostly LIFO with an occasional pop from the other end for fairness, and netpoll and timers would become per-P so stolen goroutines return to their home P. GC workers and gray queues would also be per node.

How far it got. Only groundwork was written: CL 5461, “runtime: system topology discovery” (+1548/-12, February to April 2015), whose entire message is “DO NOT REVIEW”. It stayed open. The doc describes the design as an infrastructure proposal to be refined “once we implement it and gather more information”, and no scheduler, allocator or GC changes were posted.

Why it stopped. No reason is recorded in the CL or elsewhere: CL 5461 has no review messages and no abandonment, and the design was never implemented. The only stated reservations are in the doc’s own “Risks” section. Several processes could pick the same NUMA node and oversubscribe it while other nodes sat idle, and a large structure allocated on one node and used by all goroutines would make that node’s memory bus a bottleneck.

Lessons. Vyukov’s doc warned that “even this relatively modest affinity scheme has potential to degrade an application performance”, and that benefits “significantly diminish” if affinity fails at any level of the core, M, P, G and memory chain.

Several attempts in spring 2016 to make the linker read object files faster or with less memory: memory-mapping input and avoiding copies, reading each object file fully into memory, a section-oriented object format, an uncompressed zip as the object container, and splitting object sections into independent length-prefixed chunks so they could be parsed in parallel.

How far it got. David Crawshaw’s CL 20104 cut LinkJujud by 2.67% (-6% at one patch set). Hudson-Doyle’s CL 20126 reported linking juju 21% faster (35% with -w) but failed the gdb runtime test. Kohanim sent CL 20175, CL 21020 and CL 21752 (LinkCmdGo -3.62%); Hudson-Doyle’s CL 21444 measured LinkCmdGo MaxRSS -10.6% but LinkJuju +7.4%. Most were abandoned or marked “DO NOT SUBMIT”.

Why it stopped. Each CL ended differently. Crawshaw wrote on 2016-03-16 that following review suggestions “has slowed down the code so now this CL is a wash” and that “linker performance is a diversion from my binary size goals”; Brad Fitzpatrick answered “I think we can get the same speedup or more via other cleanups”, and it was abandoned on 2016-03-21. Kohanim abandoned CL 20175 because it “slows down linking with a cleared page cache”; Fitzpatrick had been “wary of slurping everything into memory”. Hudson-Doyle abandoned CL 20126: “All the interesting bits of this have been done in other branches now”, and called CL 21444 “very dead” in 2019. Russ Cox wrote on CL 21020 that it was “a major rewrite of the object file format and is possibly incompatible with other plans for converting the overall outer archive to .zip” (the zip proposal was #14386). On 2016-10-12 he marked CL 21020 and CL 21752 “R=close”, writing “I’d like to look at all of this again in Go 1.9”. In #11123 on 2016-12-19 he wrote: “This is a good idea, but right now we don’t have the bandwidth to help redesign the object format and support the resulting churn in the code base… Marking this declined for now.”

What landed instead. The object-format redesign was done later in the linker work described in the new object file format and loader; the speed work of the period is in linker speed and memory.

DWARF type generation in the compiler

dormant 2022-04 → 2023-05 · guangyuan zhou · 17 CLs

What was tried. Moving generation of DWARF type DIEs out of the linker (cmd/link/internal/ld/dwarf.go) and into the compiler, so that each compilation unit emits its own type information. The series defined a dwarf.Type interface in cmd/internal/dwarf, implemented it for the compiler’s types.Type, synthesized the pseudo types for map, slice, string and channel in the compiler, and finally deleted the linker code. The stated motivation in #52209 was that dynamically linked programs (plugins, -linkshared) could not be debugged, and, as the issue quotes, @thanm had floated the move earlier.

How far it got. guangyuan zhou opened #52209 on 2022-04-07, with a working initial version, then split it into a series of about 31 CLs from 2022-04, including CL 399059, CL 399294, CL 399302, CL 399275, CL 400137 and CL 400138 (-916 linker lines), plus -linkshared support (CL 400634) and tests (CL 404217). It was rebased in August 2022. The last CL updates are in April and May 2023.

Why it stopped. No reason is recorded in the CLs or the issue. Ian Lance Taylor wrote on 2022-04-07 that this “doesn’t have to go through the proposal process” and that the linker/compiler/runtime team could decide. Matthew Dempsky put Code-Review-2 on CL 399877 (moving map and slice prototypes into the compiler’s builtins) on 2022-04-14 without a recorded comment. The author asked for review on 2022-08-12 and again on 2022-09-26 (“Could we continue to review these and make it more closer to merging?”); the issue records no reply, and 14 of the 17 CLs remained open with no further activity.
