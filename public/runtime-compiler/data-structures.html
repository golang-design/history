Hash map core: from the first hashmap.c to the 8-entry bucket design

Span: Go 1.0 → Go 1.17 · Status at go1.17: still the design at go1.17 (array of 8-slot buckets, tophash bytes, chained overflow, incremental growth) → continues as Swiss-table maps (GOEXPERIMENT=swissmap → only implementation) (1.24+) and Classic map maintenance and maps package helpers (pre-swiss) (1.18+)

Design. The first map implementation is src/runtime/hashmap.c (2008, “mike’s map code”, bc0b4f0d2a; an earlier map.c was removed by that commit). In 2008 keys of pointer type were allowed by treating them like ints (5adbacb8e7). The table was a chained hash table whose pieces were freed on resize in 2010 (21518ea2af); large values were supported by b198c8612e; the spec rule “a missing key yields the zero value” was implemented in the runtime in 2010 (e781303e27) and descriptive panics for writes to nil maps followed (f2852ba618). Range over a nil map and deleting from a nil map were made legal (86145611b0, 28a50c7f51).

The structure that shipped as the long-lived design is Keith Randall’s rewrite (00224a356a, Go 1.1): the hashtable is “an array of 8-entry buckets with chained overflow. Each bucket has 8 extra hash bits per key to provide quick lookup within a bucket. Table is grown incrementally.” The commit reported Go time dropping from 0.51s to 0.34s and added hashmap_fast.c (specialized lookups, see the fast-path thread) plus compiler changes in cmd/gc/walk.c. The Hmap header shrank to a 48-byte allocation in Go 1.2 (4042b77776). Several first-bucket and lookup shortcuts followed: lazy allocation of the first bucket array (5b3ff61be6, NewEmptyMap 196→107 ns, 2→1 allocs), avoiding string hashing for small single-bucket maps by comparing lengths first (45b54ee7fb, a696ae56db), and faster range over an empty map (7b9df09261).

In Go 1.3 the runtime/compiler interface changed so that key and value are passed to map accessors by reference rather than by value (3278dc158e), part of removing vararg C calls for exact stack scanning; a shared zero-memory area, allocated by the linker for all non-reflect map types, is returned on a miss. Go 1.4 converted the whole implementation from C to Go (0c6b55e76b, “a bit slower, but not painfully so”, with the hash/eq stubs and nosplit still on the wishlist) and moved constants from the map header into the map type (668a55a882). Go 1.5 moved the overflow pointer to the end of the bucket so that pointers to zero-sized keys/values cannot point past the bucket into the next object (fbc56cf050; the nacl/amd64p32 padding fix is c5dff7282e), skipped equal(k,k) for reflexive key types (df1739c77d), and stopped scanning maps whose keys and values contain no pointers by keeping all overflow buckets alive through a separate array (85e7bee19f). In Go 1.6 the zero-value pointer in the type descriptor stopped being used: a miss now returns a runtime-owned pointer (38519e69d0) and the zero field was removed (af78482d6b); before that, reflect-created map types had their zeros allocated on demand and shared (7e26a2d9a8). Go 1.11 removed the hmap field from map types (4ebc67d334) and Go 1.12 introduced emptyOne/emptyRest slot states (4b05c01f9c). Go 1.9–1.10 added hmap.extra, covered in the growth thread.

Map growth, iteration order, overflow buckets and GC interaction

Span: Go 1.0 → Go 1.12 · Status at go1.17: still the design at go1.17 → continues as Classic map maintenance and maps package helpers (pre-swiss) (1.18+)

Design. Growth in the 8-slot design is incremental: when the load factor is exceeded (initially computed with floating point, later with overLoadFactor in integer math: 733567a186, 64-bit calculation b666f2860b, load-factor bug fix dbe3522c7f), hashGrow allocates a bucket array twice as large and each insert or delete evacuates the old bucket it touches plus one more from an advancing mark. Reads in Go 1.1 first tried to do grow work too (07b6add0ca) but this broke freebsd-386 and was reverted (7f0ee023ba); the final rule is that only writes evacuate (0e7144a875). The “evacuated” state was originally stored in the low bit of the overflow pointer; because the GC wants correctly typed, aligned pointers it was moved into the tophash entries (9aae6c1a8b).

Iteration order has been deliberately randomized since 2011 (e40d6e066a). In Go 1.3 the randomization changed from “start at a random bucket” to “start at the first bucket but walk each bucket at a random offset” (3be4d95731), which made single-bucket maps (<= 8 entries) iterate in one of only 8 orders; Go 1.4 returned to a random starting bucket for larger maps, bringing the iterate-and-delete pattern from O(n^2) to O(n log n) (55c458e05f, MapPop10000 270 ms to 6 ms) and kept intra-bucket randomness always (251daf8650).

Overflow handling got three mechanisms. First, Go 1.8 bounded overflow-bucket growth (9980b70cb4): after repeated fill-and-delete (issue 16070) overflow buckets were never reclaimed. Instead of repacking (which disturbs iterators) the runtime reuses the existing growth path with a same-size grow (“sameSizeGrow”) once enough overflow buckets have accumulated; the counter is 16 bits and incremented stochastically for large maps so the header does not grow. Second, Go 1.9 turned the pointer-free-map overflow slice into a general hmap.extra (a41b1d5052), added newoverflow and preallocated overflow buckets based on a simulation of inserting the midpoint element count for each bucket-array size (94e44a9c8e). Third, evacuation was made more consistent: the evacuation mark skips buckets already evacuated (064e44f218), and in Go 1.10 the evacuate routine was unified for X/Y destinations (77a9cb9b4c, removing a data-dependent branch said to be mispredicted about half the time), split into advanceEvacuationMark (e0b34e7be7), made an evacDst top-level type (776c33ee5e) and given specialized evacuate_fast32/64/str copies (4cf7f909c6, 3c182a12f7, db9f5917fc, 0480bfe57f, 8adaf68570) that drop handling of non-reflexive and indirect keys. Pointer-free bucket memory is no longer cleared on grow (3f972df4a7) and delete clears only pointer-containing memory (0c7fd56951). hmap.extra.overflow was split into overflow and oldoverflow fields (1d3ad6733e).

GC interaction passed through three stages: bespoke hashmap GC iterator code (Go 1.1, 1e01fba2fc), compiler/reflect-generated type information for the bucket type with that code deleted (Go 1.2, fb376021be), and in Go 1.5 skipping scan when neither key nor value has pointers (85e7bee19f). Reflect’s MapOf had to build matching bucket types (3660b532ac, 5bc1cef869).

Hash functions and algorithm tables: memhash, AES hash, fallback hash

Span: Go 1.0 → Go 1.17 · Status at go1.17: still the design at go1.17 (AES hash where available, wyhash-based fallback; per-map seeds; hash functions generated per key type) → continues as Map hashing and hash functions (memhash, aeshash, fallback hash) (1.23+)

Design. Early runtime hashing was an alg table per type: Go 1.0 replaced a uint8 algorithm id with a table pointer (b9ccd077dc), with hash and equal functions taking a result pointer so compiler-generated code could be called from C. A float64 hash bug was fixed twice in 2012 (022aac7883, facee93a86) and Go 1.1 improved continuity of the hash computation (51fe5444fa) and added the AES-NI hash, first for compound objects (6b57329268). Go 1.4 converted hashing to Go calling convention with real closures (a2a9768414, 7aa4e5ac5f for equality), made non-empty interface hashing use something other than return 0 (f098a29630) and hashed floats on bytes rather than words so maps of floats get linear performance (5fbcdb2661); aeshash was disabled at compile time on NaCl (18ab35f7ba).

The fallback hash (used on arm, power and x86 without AES) was replaced in Go 1.5 with “a mixture of ideas from cityhash and xxhash” (cda0ea1c0e: ~no slower on small objects and up to ~50% faster on large ones on ARM), seeded with startup randomness (ce5cb037d1), and the size argument was removed from hash and equal algorithms (d5e4c4061b; sizes needed by generic code come through a closure that points at an assembly stub, binary 0.07% smaller). Go 1.6 made aeshash DoS-resistant by scrambling the seed before xoring with input and using table-dependent seeds for all stripes of strings > 16 bytes, costing 4 aesenc instead of 3 (91059de095, small hashes +5–10%). Go 1.10 specialized memhash32/64 (2a56b023af), Go 1.11 implemented aeshash on arm64 (73e0c302b2, Hash64 196→73 ns), and Go 1.17 switched the 32-bit fallback to wyhash (78f9015236, Hash64 121→102 ns).

Hash-function generation changed in Go 1.14: instead of generating hash functions for every type “just in case”, only map key types get them, and interface{} keys are hashed at run time by type dispatch (36f30ba289). The hash function moved from the key type to the map type, leaving a single equal in the descriptor (cmd/go dropped from 504 to 10 generated hash functions, -1.0% size, interface-key maps ~20% slower). Go 1.15 added a pointer fast path for interface hashing (afd691c579, MapInterfacePtr -33%) and made runtime typehash match compiler-generated hashes exactly because a reflect-made map assigned to a named map type could otherwise change hash function (2b8e60d464).

Seeding and DoS: per-map seeds (85aeeadaec), seed always incorporated first (63bee953a2), and in Go 1.16 the seed is rotated when a map is cleared via the for k := range m { delete(m,k) } idiom or by clearing (93810ac1f4, 1a119edd8b).

On 2011-03-03 PtrTo/Value.Addr made it possible to take addresses to call pointer-receiver methods (e46acb091f, old Addr renamed UnsafeAddr). In April 2011 reflect moved to Type as an interface implemented for all kinds and Value as a struct (fb175cf77e, many methods renamed: Elem to Index/MapIndex, Get to Int/Float…, v != nil to v.IsValid()); the motivation was an allocation-free Value, with the first CL a wrapper over the old API. Subsequent steps: inline methods (7b6ee1a5d4), Set semantic change so that assignable values always refer to other memory (“cannot Set result of NewValue anymore”, gob test mallocs 6/6 → 3/5, 40fccbce6b), assignability matching Go plus Implements, AssignableTo, CallSlice (e1ee3b5db6), and opaque Value struct in Nov 2011 (a479a45548, JSON benchmarks about 1.8x faster). Struct tags became key:“value” convention with StructTag.Get (25733a94fd). Other 1.0 API: MethodByName, Value.Bytes/SetBytes, Value.NumMethod, Zero, PtrTo, FieldByName with embedded structs and FieldByIndex.

Value layout continued to change under GC pressure. Go 1.3 rewrote Value to separate pointer from non-pointer information, making it 4 words, “needed for precise gc and copying stacks” (cbc565a801); reflect select/chan ops stopped using interface words (873aaa59b7, one allocation per receive case). Go 1.4 shortened it back to 3 words, scalar no longer needed because interfaces always hold pointers (a1616d4a32).

Register ABI support in reflect and runtime assembly (Go 1.17)

Span: Go 1.17 → Go 1.17 · Status at go1.17: reflect assumes the register ABI only under GOEXPERIMENT=regabiargs and uses global register counts; not yet default → continues as Register ABI completion for reflect, memmove/memclr and bytealg across architectures (1.18+)

Design. internal/abi was created in the [dev.regabi] branch to hold ABI constants shared by runtime and reflect (baa6c75dce). reflect implements the register-assignment algorithm itself (28c5fed557 adds makeFuncStub/methodValueCall support): stack-assigned arguments follow the spec and compiler; zero-sized types need their alignment counted in stack offsets (a2f7067233) and the two short-circuits for zero-sized types were removed because an array of non-zero length of zero-sized elements must be stack-assigned (34b87b4a1a); spill space calculation fixed (cda8ee095e), counts undone on register assignment failure (51cd074c59), pointer register results kept alive in callMethod (ef36e4fd0e), stack-to-register translation in callMethod (9d46ee5ac4), ctxt preserved across moveMakeFuncArgPtrs (4fb74e0555), methodValueCall frame size on mips64 (41cf18eda7), and callReflect/callMethod are called as ABI0 (d446cb7cff).

reflect uses global register counts rather than the internal/abi constants so those constants can be non-zero (enabling the runtime’s spiller/unspiller) while reflect still works in ABI0, “turning two things we need to flip into one” (c5a1c2276e, 8cfbf34dd9). 27d306281c makes finalizers, reflect calls and Windows syscall callbacks assume the register ABI when GOEXPERIMENT=regabiargs is set. For the runtime and bytealg assembly, 849dba07a5 ports performance-critical functions (memmove, memclr, memequal, cmpstring-like) to read register arguments directly so builtin calls from compiled ABIInternal code avoid ABI wrappers (wrappers cost on many benchmarks, e.g. BiogoKrishna -4.6%); 8f4c5068e0 does the same for internal/bytealg; compile-time memequal_varlen is referenced as ABIInternal (411860251e) and method wrapper tail calls are disabled under RegabiArgs (45e87cd3ec).

Swiss-table maps (GOEXPERIMENT=swissmap → only implementation)

Span: Go 1.24 → Go 1.28 · Status at HEAD: only map implementation since the experiment was deleted in 1.26 (2ae059ccaf); GOEXPERIMENT=mapsplitgroup (KKKKVVVV layout) still an opt-in experiment; micro-tuning ongoing in 1.27/1.28

Earlier history: Hash map core: from the first hashmap.c to the 8-entry bucket design (Go 1.0 → Go 1.17)

Design. The classic bucket-chained hmap (8-slot buckets, overflow chains, incremental evacuation) was replaced by a Swiss table in the new package internal/runtime/maps, modelled on Abseil and on github.com/cockroachdb/swiss (0733682e5f). A map is a directory of tables (extendible hashing, d94b7a1876: “splits a swisstable map into many swisstables. This keeps grow operations small”, so there is no incremental evacuation any more; a table is rehashed/split in one go and its size is capped). Each table is an array of groups: a 64-bit control word (one byte per slot: H2 = 7 hash bits, or empty / deleted-tombstone) plus 8 slots. Lookup probes group by group (probeSeq), computes matchH2 on the control word to get candidate slots, compares keys, and stops at the first group containing an empty slot. Deletion writes a tombstone unless the group has an empty slot. Small maps (<=8 entries) skip directory and table: the map points directly at one group (77e3d8cf13) and lookups scan the group linearly (808da68c1c), later with SIMD/SWAR match instead of a byte scan (bfc209518e, ~1.7x faster for unpredictable keys, from ~25ns to ~14ns). The ABI (internal/abi/map_swiss.go) and compiler side (cmd/compile/internal/reflectdata/map_swiss.go) were forked from the old map from day one (057b703407, 4f7dc282c4) so both could coexist behind the experiment; large keys/elems are stored indirectly using the same heuristics as the old map (b5fec2cf54), concurrent-write detection (fatal("concurrent map writes")) reuses the old design (2220fd3636). Hot-path work was done by the compiler too: on amd64 matchH2/matchEmpty are intrinsified with SSE (dce30a1920; still 8-slot groups to avoid changing memory layout; 0-3% faster), and the specialised fast32/fast64/faststr variants (f782e16162) were later devirtualised for hashing (252a8adbc0). Everything else in the thread is operational polish: tombstone reuse on insert (efa43c57b1), clear erases tombstones (4e63ae46e0), pruning tombstones before growing (05ed8a00e0), proper capacity-hint handling (3b424cfa9d: no allocation at hint 0; initial capacity sized to avoid growth on average).

Earlier history: Slices and append: growslice, makeslice and string/slice conversions (Go 1.0 → Go 1.17) · Strings: concatenation, conversion and printing helpers (Go 1.0 → Go 1.17)

Design. growslice used 2x growth below 1024 elements and 1.25x above, which was discontinuous and non-monotonic. 2dda92ff6f (1.18) replaces it with a smooth formula starting after 256 elements: starting cap 256→2.0x, 512→1.63, 1024→1.44, 2048→1.35, 4096→1.30 (actual growth is larger due to size-class rounding), and growth is now monotonic in initial capacity; 256 chosen to match the total reallocation count for building very large slices. nextslicecap (1d84b02b22) factors the computation out so specialised growslice variants share it, after a micro-tuning of the loop (c56f463412). Span: Go 1.22 → Go 1.28 · Status at HEAD: stable; documentation churn

Design. iter.Pull/Pull2 convert push iterators into pull iterators using coroutines (coroswitch) between goroutines.
